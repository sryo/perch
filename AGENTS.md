# perch

Architecture and invariants for the perch MCP server.

perch exposes MCP tools for driving the user's own macOS browsers: tabs, navigation, JS evaluation, waits, screenshots, page text, accessibility snapshots, console capture, form input, file upload, notifications. It runs `osascript -l JavaScript` against each browser's AppleScript dictionary. No extension, no debug port. The tool surface is `TOOLS` in `server.js`; `SKILL.md` adds to it for skill authors rather than repeating the tool descriptions or `INSTRUCTIONS`, and `test/docs.test.mjs` keeps the two in sync.

## Architecture

```
MCP client <--stdio--> server.js <--osascript REPL--> jxaRuntime --Apple Events--> Chrome / Arc / Safari / ...
                                                          \--tab.execute / doJavaScript--> page scripts
```

`server.js` has four layers, top to bottom:

1. **Transport.** `OsaDaemon` keeps one `osascript -l JavaScript` process per lane, running `DAEMON_LOOP`, which reads stdin lines itself (`osascript -i` over a pipe evaluates nothing until EOF on macOS 27.2). `jxa(script, {lane})` runs a script there, falling back to one-shot `execFile` only when the script never reached stdin.
2. **JXA runtime.** `jxaRuntime()` is a real function whose source is sent once per daemon as the prelude. It defines `globalThis.__perch` with the per-call entry points. Node calls `rt(fn, args)`, which sends one short line: `__perch.fn(<json>)`, wrapped in an IIFE that clears the runtime's note (`takeNote`) before the call and reads it after. A non-empty note rides ahead of the result as JSON between `NOTE` markers (`\u0001`): `s` the handle a page was stamped with, `m` that handle again when it differs from the one the call came with (a moved tab), `c` Safari windows' tab counts per handle; `rt` strips it and records them (`stampedHandles`, `movedTo`, `stampCounts`).
3. **Page scripts.** `PAGE_PRELUDE` plus `PAGE_SCRIPTS[name]` are plain strings that run inside the tab. `pageScript(name, A)` ships their `lean` forms (comment lines and indentation dropped once at load, so page call payloads are about 22% smaller; they hold no backtick, block comment or line continuation), prepends `const A = <json>`, and `buildEvalWrapper` wraps the result. Helpers only some scripts call ship only with those scripts (`CLICK_LIB`, `TABBABLE_LIB`, `SELECT_PICK_LIB` beside `SELECT_LIB`, `TA_UI_LIB` beside `TYPEAHEAD_LIB`, `CENSUS_LIB` for the snapshot and `fill_fields`), so `fill_fields` carries no click or picker code; perf-budget checks every script defines each such helper it calls.
4. **Tools.** Thin Node handlers (`HANDLERS`) validate arguments, call `rt` or `evalJs`, and shape results. `formatResult` maps them to MCP content.

**osascript daemon.** A warm REPL runs a realistic script in about 25ms against about 90ms cold. That saving is JXA bridge startup, not the fork.
- **Lanes:** there are two, `fast` and `slow`, so a polling `wait`, `select`, `navigate` or `awaitPromise` never blocks quick calls.
- **Per-tab serialization:** `fill`, `select`, `file_upload`, `click {readback}`, `click {trusted}`, `press {trusted}`, `wait {quiet}` and `screenshot {ref|selector}` keep state on window globals between page calls, so `handleCall` runs them one at a time per `target.tabId` (`withTabLock`; untargeted calls share one key). Other tools and other tabs never wait. A targeted and an untargeted call on the same tab are not serialized, and neither are calls from two perch servers; `click {readback}`, `wait {quiet}`, `select`, `fill`'s typeahead pick, `file_upload`'s drop fallback and a new-tab click's second pass tell their own page state from another server's by an owner token (`TOK_LIB`'s `rbTok`; Timers, Select, Drop zones, Clicks that open a tab).
- **Framing:** each script is URI-encoded onto one line and evaluated inside an IIFE that prints a `<<P:<id>:O|E:...>>` marker. `encodeURIComponent` always escapes `<`, `>` and `:`, so markers can't collide with the payload. Output is scanned incrementally.
- **Start-up:** the prelude round-trip is the ready handshake; there is no fixed settle delay. The server calls `warm()` on both lanes once it is connected, so no tool call pays the cold start (live, a first call 800ms after start: 183 to 109ms on the fast lane, 199 to 60ms on the slow one). It never throws: a failed spawn leaves no process and the next call retries.
- **Failure policy:** a timeout or a mid-call exit rejects and kills the REPL, and the next call respawns it. So does `abort(err, token)`, which the dialog watchdog uses; it acts only while that job is still running. None is retried, because the script may already have opened a tab or posted a click. Only a script that never reached stdin (`notSent`) falls back to one-shot.
- **Off switch:** disable the daemon with `PERCH_DAEMON=0`.

**Targeting (`resolve`).** `procs()` does one `CGWindowListCopyWindowInfo` read, about 4ms. It gives the on-screen z-order of browsers, the frontmost app, and pids and CGWindowIDs. It replaces a System Events `frontmost` query, which took about 60ms per call and needed Automation permission for System Events.
- **Search order:** candidates are on-screen browsers topmost first, then the rest of `BROWSERS` in declared order, checked with `running()`.
- **Stopping:** the walk stops at the first match.
- **Window ids:** `win.id()` is read only when `windowId` was given.
- **Default target:** with no target, the active tab of the first window, read first as `windows[0].activeTab.id()` of the first candidate (one event on Chromium and Arc). A window showing no tab (a fresh Arc window) is skipped.
- **Tab handles:** clients never branch on browser. `tabId` is an opaque handle `<key>:<raw>` (`key` from `BROWSERS`, e.g. `arc:<uuid>`, `canary:<id>`), so `{tabId}` alone targets a tab in any browser. The key matters: Chromium tab ids are per-process counters and collide across Chromium apps. Safari tabs have no id, so theirs is `safari:<windowId>.<index>.<url hash>`: `resolveSafari` re-finds it by URL within its recorded window, and a navigation makes it stale, which is why `navigate` returns the tab's current handle. Outside that window it resolves only when exactly one tab app-wide shows the URL (a dragged-out tab); with several it is `stale_tab`, so a gone tab never lands on the user's tab at the same URL. Which of the URL's tabs is the handle's is settled by a stamp: the guard on a handle's first page JS in a call (`stampGuard`, in `quickExec` and `pickRun`, inside the same `doJavaScript`, so no extra event) checks the URL hash, then the page's stamp in `window.__perch_h` by mode, and writes this handle's raw id there before the body runs. Mode `any` takes any stamp: a never-stamped handle at its recorded index (`quickExec` for a handle not sent as `target.own`, `pickRun` at the recorded index). Mode `free` takes the handle's own stamp (its raw id or one it was refreshed to) or none; mode `ours` takes only its own, and an unstamped page answers `UNSTAMPED`. So `free` and `ours` refuse a page whose `window.__perch_h` names another handle, and `any` refuses only the stamps sent as `target.foreign` (below). Node keeps the handles that have stamped (`stampedHandles`, sent as `target.own`); for those, an unstamped page at the recorded index is not taken in one event but left to `pickRun`, which tries the recorded index first, then the nearest, one event each, until a page carries the stamp. For a handle that never stamped, a single tab at the URL in the window runs (and is stamped: mode `any` at the recorded index, `free` off it); with several, the one at the recorded index runs in mode `any`, and only when none is there (and none carries its stamp) is it `stale_tab: can't tell which tab ...; several tabs show its URL`. A handle that has stamped never adopts an unstamped page off its recorded index (`stale_tab: can't tell which tab ...`), since once its tab is gone that is the user's. At the recorded index an unstamped page is either its own reload or a same-URL tab that slid in after its tab closed, and nothing on the page tells them apart, so it runs only while the window's tab count at that URL and its total tab count match the last read (`stampCounts`, sent as `target.cnt`; `note.c` from the runtime). Those counts come only from reads a call already makes, and Node keeps them only for a handle the call's result issued (`issuedHandles`: `list_tabs` rows after `urlContains`/`limit`, `new_tab`, `navigate`, a click's `opened` tab) or the one its pick stamped (`keepCounts`): a listing's rows, `new_tab` (whose one `tabs.url()` read replaced the length and URL reads), `navigate`'s handle (`handleOf(t, true)` reads the window's URLs where it read the tab's; other `handleOf` callers record nothing), a click's opened tab (the `after` read), and a pick in `pickRun` (the window read `resolveSafari` made). A listing that leaves a handle out never refreshes its counts. The one-event in-place hit reads none, so they keep the last read. A stamped handle with no recorded counts is refused the same way, and past `STAMP_LIMITS.counts` only the counts are dropped, so stamped handles fail closed. `stampedHandles`, `movedTo`, `issueSeq` and `stampSeq` (below) are each capped at `STAMP_LIMITS.stamped` and drop their least recently used entries; once one has been dropped, a Safari handle Node doesn't know is held to the stamped rules (before that it counts as never stamped: a server restart, a hand-built handle), and so is one issued before the latest dropped stamp, so eviction fails closed too. So a stamped handle whose page reloaded after the user opened or closed tabs in that window since the last read is `stale_tab`; re-run `list_tabs`. Residual: a same-URL tab opened after that last read, then the agent's tab closing so it slides into the index, brings both counts back and still runs; and a never-stamped handle still runs on a same-URL tab that slid into its index when that tab is unstamped or was stamped before the handle was issued. A tab found off its index answers `moved: true` with its refreshed `tabId` (`eval_js`: in a second text item), so the next call is a one-event hit again; the older handle still accepts the refreshed one's stamp (`movedTo`, sent as `target.next`). A handle `list_tabs`, `new_tab`, `navigate` or a click's `opened` tab just issued counts as never stamped, since the listing vouches for its index: it runs on the page there in mode `any`, whatever that page's stamp, or a re-listed tab stamped under its older handle would be refused for good, except a stamp written after it was issued: Node dates issues (`issueSeq`, in `handleCall`) and stamps (`stampSeq`, in `rt`) on one clock and sends the handles that stamped a tab in its window at its URL since then as `target.foreign` (more than 20 hold it to the stamped rules). `stampGuard` mode `any` refuses those, and `pickRun` then looks only for this handle's own stamp on the other candidates, else `stale_tab`, so a tab that slid into its index after another handle stamped it is never run. Only handles stamp pages; the default target and `tabIndex` don't. `close_tab` is strict: only the recorded window, and only the tab at the recorded index, when it still shows the URL; a tab that moved is `stale_tab`, since the one at its URL may be the user's. A bare id from before handles is still searched across browsers.
- **Tab ids:** a handle resolves with one bulk `win.tabs.id()` read per window, then `tabs.byId`. Chrome and Arc targets are pinned by id even when given by position, because `tabs[i]` is re-evaluated on every use and a long poll could drift to another tab. Chrome has no tab `select` verb, so selection re-reads the position from the id.
- **Apple Event budget:** live, each Apple Event to a browser costs about one display frame (~16.7ms), while `procs()` and `running()` cost under 3ms, so latency is the event count; `test/perf-budget.test.mjs` pins it. `evalJs` first tries `quickExec`, one event: a Chromium handle through its remembered window (`hints`, filled by list_tabs, new_tab and resolve; `windows[w].tabs.byId(id)` can only miss, never hit another tab), a Safari handle through `windows.byId(win).tabs[i]` with the page checking its own URL hash and stamp first, or the default target's active tab. It falls back to `resolve` only when the script cannot have run (errAENoSuchObject, or the hash or stamp sentinel). Arc handles keep separate `arcHints` (a window that showed the tab, from list_tabs and resolve; never new_tab, whose tab is put behind), checked with one `windows[w].activeTab.id()` read; a hit or the default target marks the tab `shown`, so `isActive` costs nothing more: an Arc page call is 3 events (shown tab, url, execute). `wait`, `awaitPromise`, `select` and click readback only run page JS, so a hinted Chromium handle builds its tab with no event (`pageTarget`) and re-resolves once, on errAENoSuchObject only. Every page call and tab read goes through `onTab`, which does that for any tab with an id (`windows[w]` is positional, so a raised window can make a pinned tab miss); a tab found nowhere, a second miss, or a Safari tab (no id to re-find) is `stale_tab`, and `poll` and navigate's loops end on it at once instead of polling to a timeout. `wait` tries `quickExec` first, then polls every 50ms. `list_tabs` reads all of an app's windows at once (`windows.tabs.url()` and friends: four events for Chromium and Safari, six for Arc), and a `urlContains` or `titleContains` no tab of a browser matches stops that browser after one read. Each browser's lister is a generator that yields after every event, and `listTabs` runs them in turns, one event each: frame phases differ per browser, so three browsers take about as long as the slowest alone (fake frame clock: 208 to 102ms; live with Canary, Arc and Safari open, `limit:10000` went from 205 to 101ms, and one browser alone is unchanged at 67ms), and a failed bulk read walks windows in the same turns and the same slot. Each browser reads first what its filters look at (urls when there is none; Arc its tab ids), and a browser whose earlier browsers are sure to fill `limit` (their exact rows once listed; before that, their first read: exact for Chromium and Safari with one filter, distinct ids or the best single window for Arc, nothing with two filters) is only counted for `total`, from the reads it already has. `test/list-tabs.test.mjs` checks rows and total against per-browser listings in random worlds. Window geometry is one `bounds()` read (Chromium fails `position()`, Safari only has `bounds`, and a failed read costs a full event); on Arc it is one `windows.name()` read. Never touch a quit app's windows (`alive`): JXA relaunches it.
- **Browser names:** `matchApp` (Node, in `handleCall`) matches `app` loosely: case-insensitive name, key, or a unique substring.
- **Errors:** thrown errors start with a browser-neutral code (`tab_not_visible`, `stale_tab`, `window_offscreen`, `no_browser`, `timeout`, `dialog_open`, `tab_not_scriptable`: a browser-internal page page JS can't run on; `bad_url`: a `navigate` or `new_tab` url that is not absolute http(s), `file://` or `about:blank`, where `file://` stays loadable by decision since avis opens local prototype files with it; all of them in `CODED`), plus two outside `CODED` that trusted input and the frame walk throw: `window_ambiguous` (another window of the browser has the same frame, or two instances of the browser have windows on screen) and `frames_unreadable` (Accessibility could not read the page's frames) that clients branch on. Tool descriptions and `INSTRUCTIONS` never name a browser; `test/runtime.test.mjs` enforces it. Permission messages are the exception, since the user needs the exact per-browser toggle. `tab_not_visible` never activates the tab for the caller; that is `activate_tab`'s opt-in.
- **Raw AppleScript failures:** the daemon appends an Apple Event error's number to its message (`Application isn't running. (-600)`), as one-shot stderr already does, and `codeOsaError` (in `jxa` and `formatOsaFailure`) maps it: -600, -609, -903 and -10810 (the browser quit, its connection is gone, or it can't be reached) to `no_browser`, -1712 to `timeout` (its wording is a `HANG` phrase, so the dialog probe runs), -1728/-1719/-1708/-10000 to `stale_tab`, -1743 and the JS-from-Apple-Events wording to the permission messages, and a lane that died (`osascript exited mid-call`) to `timeout` that says the call may have run. The number stays as a suffix, `(AppleScript -600)`; a number not in the map keeps AppleScript's own message with that suffix, and -2700 (a script's own throw) keeps its message bare. A browser that couldn't be read (denied, unanswered, its handler failed, or quit) is also why `resolve` found nothing, so it throws that error instead of `no_browser: no browser window`, except that a browser whose handler failed or didn't understand the event (-10000, -1708: busy, starting up or behind a dialog) is a transient `timeout` naming it and saying to retry in a moment, since no tab matched to go stale. `list_tabs` skips a browser that quit, but one it couldn't read fails the call when nothing else listed, and is a `warning` beside the other browsers' tabs otherwise: an empty list always means no tabs. `list_tabs` never answers `stale_tab` (a listing names no tab, and "re-run list_tabs" would only repeat the call): `listFailure` turns what would code as `stale_tab` into a transient `timeout: <app> did not answer the tab listing` that says to wait a moment or pass `app` for another browser.

**JXA access patterns.** Read collections lazily (`app.windows[i]`, `win.tabs[i]`), never with the called form (`app.windows()`). The called form loses the bridge context on Arc, and later property chains throw "Can't convert types". Multi-tab reads use bulk property access (`win.tabs.url()`), about 30x faster than per-tab loops. That's the difference between working and timing out on Arc windows with hundreds of tabs.

**Arc quirks.**
- **Double encoding:** Arc's `execute` JSON-stringifies whatever the page function returns, so `exec` unwraps one layer.
- **Reading the active tab:** `win.activeTabIndex()` and `win.currentTab` both throw. `win.activeTab.id()` works; it throws on a window showing no tab.
- **Tab order:** `win.tabs` order is unrelated to the sidebar (effectively random) and includes Favorites (`location` `topApp`). `win.activeSpace.tabs` is in sidebar order. `arcOrder` builds the display order (Favorites, then the active space's sidebar), and Arc's `tabIndex` means a row in it.
- **Shared windows:** windows on the same space share the same tab set (same UUIDs), and one tab can be active in several windows. `execute` works only through a window where the tab is active and hangs through any other, so `resolveById` prefers such a window. `select` changes only the window it's called through. `list_tabs` lists each Arc tab once, under the frontmost window showing it.
- **Switching tabs:** writing `activeTab`/`currentTab` is forbidden, but `tab.select()` switches without raising.
- **Background tabs:** `execute` hangs until timeout on a background tab and on its own `arc:` pages, so `visibleGuard` refuses first; `trustedTarget` refuses an `arc:` page for every trusted input, and `navigate` from or to one runs no page JS: it is refused (`tab_not_visible`) unless the call passed `raise:true` or the tab's window is already in front (see Navigation), and then sets the url and waits until the tab reads a non-`arc:` url (set again after 1s, as `new_tab` does).
- **Geometry:** Arc has no window geometry verbs, so its frame comes from its own CGWindowList entry, matched by window title (`byTitle`). AppleScript windows and CG entries both run front to back, so same-titled windows pair up in order, but only when every window with that title has an entry; without CG titles (no Screen Recording grant) windows pair by position only when every window has one. Otherwise it is `window_offscreen`, since a minimized window has no entry and the pairing would name another window. Elsewhere `ids()` takes the CG entry nearest the window's frame, and only within 4pt in x and w and 120pt in y and h (the titlebar and toolbar CG counts), else `window_offscreen`; when another of the app's entries scores within 2pt of it, `ids()` marks the match `ambiguous` and trusted input and the frame walk refuse with `window_ambiguous`; screenshots refuse too unless AX names the window (`axNamed`: exactly one AX window titled like the target's window whose `_AXUIElementGetWindow` id is among the tied entries). `axPageArea` likewise takes the one AX window within 8pt of that frame (`axWindowsAt`, shared with `axNamed`), or, when `_AXUIElementGetWindow` reads their CGWindowIDs, the one whose id is the target's; zero or several is null (no page area).

**Eval runs in an isolated world (Chrome family).** Chrome runs Apple Events JS in an isolated world. The DOM and `location` are shared with the page; JS globals are not.
- **Persistence:** globals set by one eval persist for later evals; `window.__perch_refs` and `window.__perch_console` rely on this.
- **Page globals:** the page's own globals are invisible, so probe page state through the DOM.
- **Events:** a plain `click` still fires main-world handlers, because DOM events cross worlds.
- **Console:** `console_capture` injects a `<script>` that patches the main world's console and relays entries as `perch:console` events. A ping/pong tells whether it ran; under a CSP that blocks inline scripts it patches the isolated console instead, which sees only perch's own evals. Besides `level: text`, the same hooks record three `error:` kinds: `Uncaught <Name>: <message> (<file>:<line>:<col>)` from window `error` events (a resource load failure fires on its element and is skipped), `Unhandled rejection: <reason>` from `unhandledrejection` (an Error reason is recorded with its stack), and `Assertion failed: <args>` from a falsy `console.assert`; `stop` removes the listeners and restores `console.assert`. Servers share one capture per document: `start` counts, only the last `stop` unhooks (earlier ones answer `stillCapturing`), and each drain bumps a page generation, so a read after another server's drain adds `partial:true` and a note instead of a whole-looking `entries:[]`; Node keeps the last generation seen per capture id. Not yet checked live: Chrome reports uncaught errors and rejections in the world that raised them, so the isolated-world fallback is expected to miss the page's own and see only perch's.
- **Network:** `console_capture {mode:"network"}` reads Resource Timing (`performance.getEntriesByType("resource")`), which the browser buffers without help, so it needs no start and intercepts nothing. A cursor on `window.__perch_net` drains new entries; the first read raises the buffer from 250 to 1000. Safari has no `responseStatus`, so status reads `-`. Patching `fetch`/XHR was rejected: it is close to interception.
- **Timers:** page timers are throttled to about 1/s in background tabs. Anything that must wait polls from JXA (`poll` in the runtime) instead of `setTimeout` in the page. `select` is start/pick/readback steps polled that way, and so is `click {readback}`: the click stores the readback element's text, a state signature and the url on `window.__perch_rb`, then JXA polls `readback_read` for up to 2s until any of them changes (a missing `__perch_rb` means a new document), or until the page has been quiet for 10 polls in a row (about 670ms live): no DOM mutation anywhere, seen by a MutationObserver armed with the state and disconnected on every exit, and no fetch/XHR resource timing entry completing. Other perch servers (one per Claude session) can drive the same tab, and `withTabLock` is per process, so the record carries an owner token (`rbTok`: a per-document counter, `window.__perch_tok_n`, plus a random suffix, made in the page like screenshot's, so no script carries a per-call value): the arm returns it (the click's `rbTok`, or `readback_arm`'s `tok` for trusted clicks), every read answers with the token of the record it read (`{pending, tok}` while it keeps polling), and the runtime compares it after each poll and the final read. Another token means another call armed over this one, and ends the call at once with `timeout: click sent, but another perch call on this tab took over its readback state; the outcome is not verified`, never `navigated` or `changed`. The final read no longer deletes the record: it stops the observer and leaves `{done, tok, out}`, which the next arm replaces, so a missing record still means only a new document. The record keeps the selector it was armed with (`sel`) and every read of it measures that element; a foreign poll whose `readback` is another selector answers `{pending, tok}` from the record and changes nothing in it, so a call's element is never compared with another call's baseline. A foreign poll on the same selector runs the same read on the record it finds, so it can be the one that finishes it: `out` keeps the outcome when that read saw a change (it holds against the record's own arm, whoever read it), and the owner's next poll returns it; a record finished by a settle or a final read (either may have come early for the owner) keeps `out: null`, and its owner refuses as above. A foreign poll that finds the record still pending can count one extra quiet poll toward its settle. When `document.visibilityState` is `hidden` (a background tab or a minimized window) the quiet stretch must also last 1200ms of page time (`Date.now()`, which is not throttled), so a `setTimeout(..., 300)` validation that the throttle pushes to the next ~1s tick still lands inside it; the 2s cap is the same, and a visible tab's timing is unchanged. Pending timers are not counted. An update landing later than that with nothing happening in between reads as `changed:false`. The signature covers the element and its first 50 descendants: `aria-pressed`/`-checked`/`-selected`/`-expanded`, `disabled`, the checked state and value of inputs and the selected state of options, so a toggle that changes no text still reads `changed:true`; `class` stays out, since hover, focus and animation flip it during the poll; `readback` stays the text. The rejected fields count too (`INVALID_LIB`'s `invalidSet`, computed inside the same page calls, so no extra Apple Event): a field that turns invalid or changes its message, or one whose error clears, ends the wait as `changed:true`, and when some were added or reworded (a field matches its armed self by element, or by name after a re-render) a result that did not navigate adds `invalid: ["Location: Please enter your location", ...]`, every invalid field in document order, at most 5 (`invalidCount` when more), each clipped to 140 chars and named by its label, else `ident`, and a radio or checkbox by its group's name or legend. Errors already there before the click, or only cleared by it, add no key. The same arm records the clicked element's form scope (its `<form>`, else an enclosing `[role=dialog][aria-modal=true]`/`dialog[open]`, else the nearest ancestor below body, at most 8 up, holding 2 or more fields; only when it has a box), its step (`STEP_LIB`'s `stepOf`: `aria-current=step` as index/count in its list, else a progressbar's `aria-valuenow/aria-valuemax`, else "Step n of m" text in the first 200 chars, searched in the scope and up to 2 ancestors) and the visible `[role=alert]`/`aria-live` texts that are not a field's own error. A read then adds `form` only when something moved: `gone:true` (disconnected or no box), `step` (a new value; only when one showed at arm time) or `alert` (new texts, clipped to 140); each ends the wait. A read with no state (a new document) adds `page` only when it has a key: `heading`, the first visible `h1`, else the first visible `h2` (clipped to 120, since a header or nav can push it past the 300-char readback), and `alert`, the new document's `rbAlerts([])` joined with ` | ` (clipped to 140). perch reports structure, never success judged from the site's words. A submitting control (`rbSubmits`: an input or button of type `submit`, or a `<button>` with no `type` inside a `<form>`) whose own text or disabled state is the only change is mid-flight ("Submitting..."), whatever the readback is on (the button, the form, `body`): the poll keeps going to the quiet window or the 2s cap instead of ending there, so a form replaced after it still reads `form.gone`. A clear the page defers past the event (a microtask, a timer) lands after the pass that caused it, so only a later pass sees it.
- **Compile-cache exception:** the late checks (**Late reverts**) carry owner tokens in their source: a batch's `fill_reread` gets its record's token from the runtime, which swaps it for the placeholder `FR_TOK`, and `fill_late` gets the pending tokens in `A`, so every check is new source and misses Chrome's compile cache. The token is what keeps one server's check off another's record, and the page's queued work runs only between page calls, so it can't ride the write's source either. Measured cost, under Node's V8 (`vm.Script`, the 13.4KB wrapped script): about 0.2ms to compile a new token against 0.001ms for a cached source; not measured live. Nothing else in the fill or select write passes varies per call. The call after a fill or native select is a second exception: its whole execute source (the late check around that call's own page script) is unique, about 44KB for a fill carrying it and 72KB for a fill {fields}. Measured under Node's V8 (`vm.Script`, fresh source, best of 30): 0.49ms and 0.87ms; Chrome's full parse is likely 1 to 2ms per such call, not measured live. Only that one call pays it; a call with no pending token ships its script unchanged.
- **Late reverts:** a page can undo a write a task after it (a timer or a promise its input handler queued), after the page script returned. A plain `fill` asks for a record (`fr: true` in `A`): `fillOne` keeps the field it landed, what it read back and what the field held before the write (`prior`, which `onLand` hears) on `window.__perch_fr` under a fresh `rbTok` (at most 20 records a document) and returns the token as `fr`; the `select` tool's native pick does the same (`select` passes `fr: true` to `select_start`, never from `fill`'s own combobox calls; `frRecord` is in `FR_LIB`, which `select_start` ships with `HOLDS_LIB`); a `fill_fields` write pass that ends the batch does the same for every field in `__perch_ff` it wrote to: a native select's shown option text and value and the one it showed before, a checkbox's state, a radio's group and the option on before it. A box or radio already in its wanted state is not clicked, so the page heard nothing to undo there; it stays in `__perch_ff` for the later-field checks but is not recorded, and a batch of only those has no re-read (1 event, not 2). `frJudge` (`FR_JUDGE_LIB`: `HOLDS_LIB` plus the judge) reads each recorded field that no longer holds: back at its prior value, or emptied (a select on no option or a `value=""` placeholder, a radio group with none on), is a revert, `recheck` entries `{ok:false, kind, el, kept|checked, reverted:true, error: "... after it was filled; the page reverted the write"}`; any other value of a text field (a page that formats `sw1a 1aa` as `SW1A 1AA` or `1000` as `1,000.00` a task later, or another perch server's write) is a `notes` entry, `"... changed to \"X\" after it was filled; another value replaced it"`. A select or radio group on any other option is a plain miss, `{ok:false, kind, el, kept?, error: "... changed to \"X\" after it was filled; the page chose another option"}` (a radio picked by `checked` that lost its place names no option: `is no longer selected`), since no page formats one option into another. A select a batch wrote after another select, radio group or text field, back at its prior option or emptied with the option it picked no longer in it (its list rebuilt, as a country's `change` reloading its regions a task later does), is still `reverted:true` but ends `"... after it was filled; the page rebuilt its options, and fields[k] (<that field>) may have changed them; fill it again once that settles"`, naming the nearest such earlier field the record holds, since the page likely did not refuse the write; a checkbox drives no list and is never named, and with no such field the plain revert wording stays; the record keeps the picked `<option>` (`o`, read as `el[sel]` to stay inside the fill page script's size budget) for that. A select holds when it shows the same option text, or the same non-empty value, so a page that rebuilds its options around the choice is no revert. A field that left the document is not judged.
  - **Single fill and native select: the next call checks.** A plain `fill` or a native `select` answers from its write alone (1 page call; a re-read in the same call costs one more Apple Event, a frame live, and can't run on Arc and Safari, which have no bounded page call). Node keeps the token (`lateKeep`) in `lateToks`, one list for the server (at most 20), not per target: the tab a record lives in may be named by `tabId` or be the untargeted default, and the user may switch tabs. The next call whose runtime entry runs page JS (any tool but those in `DIALOG_BLIND`), on any target, carries the check: `rt` sends `lateTemplate`, which wraps `fill_late` (`FR_JUDGE_LIB`, the tokens and `hold` in `A`) and a placeholder (`LATE_JS`) for the page JS, and the runtime's page-JS senders (`execOnce`, `quickExec` and its `run`, `asExecute`) put the first script they send in its place (`lateWrap`), so the check runs first in that script's own execute: no Apple Event of its own, on every browser, Arc and Safari included. The check reports only reverts and other options, as `{el, error}` with the error after the element's name (`was cleared after it was filled; the page reverted the write`, plus `; retry with fill {trusted:true}` for typed text, not for a clear); a reformat is not reported. It answers `{l, f}` (`f`: the tokens whose records this document holds) ahead of the script's string result with a mark (`\u0002...\u0002`), which `lateOut` strips into the runtime call's note; a script that answers a non-string (a bare probe) takes no mark, and the next page JS in the call carries the check again. The check deletes nothing in the page: Node drops a token only once an answer that found its record has arrived, and a token never found (another tab, a new document) after 20 checks (`LATE_TRIES`) or 60s (`LATE_AGE_MS`), so a call on another tab first leaves it for the call on its own tab. A call that throws after its check answered (a `wait` timeout, `stale_tab`, a later page error) carries the answer ahead of the error's message (`LATE_ERR`, `\u0003`, added by `rt`'s envelope and taken off in `rt` before anything reads the message), and its error result gets the list as one more text item; an answer lost with a dropped reply leaves the tokens, and the next call reports it. The call's result gets `late: [...]` when the list is not empty (an object result as a key; text, an image, `eval_js`'s value or an error as one more text item). A `click` or `press` is held by a non-empty list (`hold`): the wrapper returns only the mark, `lateOut` throws, every later send in the runtime call throws before any Apple Event (`lateHeld`, rethrown past `pollExec`, `boundedAt`, `stepExec` and `poll`), and Node answers `{ok:false, error: "nothing clicked: a field filled earlier no longer holds its value (late); fill it again (fill {trusted:true} if the page converts or clears it on blur), then retry", late}`, so a submit never goes out with a field the page emptied; the tokens it reported are dropped, so the next click runs, and a tag or chip input that empties on blur by design holds a click once, not in a loop. A trusted click with `raise` has raised by then. Owner tokens keep one server's check off another's records, which it never reports. In a background tab page timers run about once a second, so the later check catches a timer's revert that a re-read a frame after the write missed.
  - **fill {fields}: the batch's own re-read.** Node hands the `fill_reread` script (with the placeholder token `FR_TOK`, which the runtime swaps for the write's `fr`) to `evalJs` as `reread`, and after a write whose result carries `fr` the runtime sends it on the tab the write ran in, capped at `POLL_EXEC_SECS`: `pollExec` on a resolved tab, else `boundedAt` on `quickExec`'s tab, a hinted Chromium tab by id or, untargeted, `execute active tab of window N` (the same window the plain untargeted path used; `asScript` builds that handler when there is no tab id), and the result comes back with `rr`. So no tab id is read for it, targeted or not. `fill_reread` deletes the record and returns `frJudge`'s answer, whose `recheck` entries replace the batch's results and whose `notes` join a field's `note`, leaving it `ok`. One page call for the whole batch keeps a revert in the batch's own answer, next to the field's index, for 1 Apple Event over 5 or 20 fields, where single fills would pay the check nowhere but would report it one call later. Arc and Safari have no bounded page call (nor does a Chromium app with a second instance running, where `pinned` is false), and an unbounded re-read behind a navigating change handler waited out the 2-minute default (Arc, fake world: 120000ms), so none is sent there: the result's `rr` is `{unbounded}`, and the batch's token goes to `lateKeep`, so the next call's check reads it as a single fill's (Arc and Safari lose no revert detection). A write whose change handler navigates (a jump or sort-by menu, a `form.submit()`) leaves an execute Chrome never answers; the dropped reply is `{dropped}` after 2s, and a re-read that failed is null: both leave the token to the next call too. A missing record (`{lost}`: a new document, or another tab after a switch) leaves the batch's answer as it was. None of these adds a note. A batch ending on a custom combobox skips it, since its recheck pass comes later still. A custom combobox needs no re-read: its option is pressed in one page call and read back by `select_read` in later ones, so a flip the page queued a task after the press has run before the first read, which then fails as `pressed ... but the control shows ...`. It can't ride the write's own execute: the page's queued work runs only after that script returns (the fake world ticks its queue between executes the same way), `awaitPromise` is itself a kick and a poll (2 events at least), and Chrome's isolated world can't see the page's listeners, timers or promises, so nothing in the write's page call can tell a field that may be reverted from one that won't.
- **Form census:** the call's last `fill_fields` pass (the one that returns no `defer`, or the recheck-only pass after a closing combobox) adds `form: {requiredEmpty, unpicked?, left?}` for `ff.form`, the form the first landed field sits in, while it is still connected: `CENSUS_LIB`'s `census` (shared with the snapshot header, so the counts match its `form` for the same form element), `left` naming the required-empty and unpicked fields in document order, at most 10, as `{name, label}` (`wantName`: the `name` attribute clipped to 120, and `accName`, or for a radio group its `question`, the radiogroup's name or fieldset legend; a label equal to the name is dropped, and a field with neither gets `{placeholder}`, `{type}`, `{id}` or `{role}`, which hidden rows fall back to as well). No extra Apple Event. Fields outside any `<form>`, a batch that returned `gone`, a halted batch, and a recheck-only pass that did not run add no `form`, so it never counts a document the batch no longer knows. `ok` still follows the results; the census is information. A wizard whose steps share one `<form>` counts its hidden steps' required fields too, as the snapshot does.
- **Fields file and preference lists:** `fill {fields_path}` reads the `fields` array from a local JSON file (at most 256KB, `readUserFile`), then validates and fills it exactly as inline `fields`, with the same Apple Events; a missing file, bad JSON or a non-array top level throws `fill: fields_path: ...`, and `fields` with `fields_path` throws. A field's `option` may be an ordered list of at most 10 strings. `pickNative` and `pickRadio` try each in order with the usual tiers before setting or clicking anything: a missing or disabled one moves on, a tie stops with that preference's `ambiguous` error (a later one never settles it), all missing returns the first one's error with `candidates` and `tried`, and a pick past the first adds `pref: i`. A custom combobox gets the list as select's `text`: `select_pick` matches every preference against the list as it shows, in order, and types only the first as its filter. Node (`selectPrefs`) runs another select with the rest only after a plain `no option of this control matched` that typed a filter (`filtered`, stripped from the result), so a list without a search box opens once. The `select` tool itself still takes a string; typeahead `text` takes no list.

**Page scripts.** One prelude defines `vis`, `labelText`/`hintText`/`accName` (accessible-name precedence), `role`, `ident` (`role "name"`), `setNativeValue` (the prototype setter, which reaches React-controlled fields), `fire` and `resolveEl`.
- **Arguments:** every tool body reads its arguments from `A`; no user value is spliced into code.
- **Refs:** a ref is valid only against the map this server's last snapshot of that tab built (the tab keyed as `tabLockKey` keys it, so a ref from an untargeted snapshot needs an untargeted call). Each snapshot names its map with a page-made `window.__perch_refsId`, returned as the header's first key (`rid`), which `takeRefsId` drops before the agent sees it. `handleCall` looks up `refMaps` for the call's tab: a ref that snapshot did not show (a server restart, another tab, an earlier snapshot) ends the call before any page JS; otherwise `pageScript` puts `rid` beside every `ref` in `A`, so the source varies only with the ref. `resolveEl` treats a ref whose `rid` is not the page's current map id (a new document, another server's snapshot), or a missing or detached one, as `{__perch_ref_miss}`, which `formatResult` turns into an error with a re-snapshot hint. The page's counter keeps refs apart within one document, not across documents or tabs, so `issueRefs` shows a ref this server showed before (the latest 50000) under the lowest unused number, rewriting its `reveal=` and `focus` too, and maps it back on the way in: a ref names one row of one snapshot.
- **Page faults:** a perch page script that throws comes back as `{__perch_error, __perch_error_name, __perch_error_stack_head}`, whose message and stack are the page's (its URLs included). `handleCall` turns any such top-level result, for every tool but `eval_js`, into `scriptFault`'s `{ok:false, error:'<tool>: the page script failed on this page (<Name>); nothing verified'}`, with no `isError`. When perch had already set `delivery` or `point` (trusted input went out), it keeps those and `el` and says the click, keys or text was sent, outcome unverified. `viewOf` throws the constant name `PerchStaleRef` when a ref's frame document lost its window, which maps to `{__perch_ref_miss}` for the call's `ref`; a page forging that name only gets the re-snapshot hint. The runtime words trusted click and press faults itself before any of that: an arm step that throws posts nothing ("nothing was clicked" / "pressed"), and a check or readback that throws after the post says the click or key was sent and the outcome is unverified. An element `screenshot` whose `shot_clip` throws has put its scroll back in the page (the runtime never restores after a fault, which could apply another call's record) and says `screenshot: the page script failed on this page (<Name>); nothing was captured` (a `PerchStaleRef` still becomes the ref miss). `wait` throws its fault with the same neutral wording (so its reply carries `isError`), and names only a selector the page can't parse (`wait: bad selector: <selector>`); only `eval_js`, whose script is the caller's, keeps the raw shape.
- **eval_js ref:** `eval_js {ref}` binds the snapshot row's element as `el` inside the same page call, so it adds no Apple Event. `composeEvalScript` wraps the body in a fixed shape: it reads the ref from `window.__perch_refs` when `window.__perch_refsId` is the ref's `rid`, returns `{__perch_ref_miss}` (so the user script never runs) when the element is gone, disconnected, or in a document that is neither the page's nor one a same-origin frame still shows (the page library's `liveDoc`, inlined as `EVAL_LIVE_DOC`, since a frame's replaced document keeps its nodes connected), and otherwise calls the body as `function (el)` (`async` under `awaitPromise`, so `await` works) with `this` kept. The ref's and its `rid`'s JSON literals are the only spliced values, and with no ref the string is byte-identical to before, so repeated calls keep Chrome's compile cache. `el` is a parameter: a script that declares `let el` throws. Frame refs (`fN`) are refused by `guardFrameRefs` before any Apple Event.
- **Snapshot:** `accessibility_snapshot` stores elements on `window.__perch_refs` (a plain object, since a Map breaks the JSON round trip). Refs continue a per-document counter (`window.__perch_refN`, seeded at 0 to 899 from `performance.timeOrigin`, so refs stay at most 3 to 4 digits; a page that leaves it unusable gets a reseed from the clock instead, so the range differs), so an earlier snapshot's ref names no row in this document's map; across documents, refs are told apart by the map id (see Refs); `max` caps rows, not ref values. It emits a line format: a `# {header}` line, then `ref role "name" key=json... flags`. `query` tests each line without its ref; refs number only the kept lines, and the header adds `matched` (all matches, even past `max`). Visibility is `vis()` plus a snapshot-local `snapVis`: a radio or checkbox shrunk or faded to nothing is listed when one of its labels is visible, and a `role=combobox` input when its styled select box (`x__control`/`x-control`) is; neither when it or an ancestor is `display:none`. A combobox input's `value` is its own, else the box's single value or chip labels, and `form.requiredEmpty` counts it filled when the box shows one; required file inputs count too, and an input that is both `aria-hidden` and `tabindex=-1` (react-select's required stand-in) does not. A select's `value` is its chosen option's text, and a select or non-input `role=combobox` box on a placeholder (`nothingChosen`: no option, a valueless or disabled one, a first `Select...` whatever its value; a box showing a placeholder element, nothing, or `Select...` text) has none and counts as required-empty; the census also takes a visible `[role=combobox][aria-required=true]` that is not an input, unless it holds a counted input of its own. `fill_fields`' `chosen` reads the same helper. `requiredEmpty` also counts an unticked required checkbox (native, or `role=checkbox` with `aria-required`) and a required radio group with nothing checked (native, keyed by name and counted once as its first shown member, or `role=radiogroup` with `aria-required`), while `fields` counts only text-like fields. The census takes the form's `form=` fields outside it too, and drops disabled fields (by attribute, or a disabled fieldset outside its first legend) and ticks under `display:none`; a required text field under `display:none` still counts, for its hidden row, whose radio name is the group's `question`. `checked` also reads `aria-checked`, and `pressed`/`selected` read `aria-pressed`/`aria-selected`. A line gets ` invalid` and `error="..."` when the element carries `aria-invalid=true` or holds a value that fails its native constraints (an empty required field stays `requiredEmpty`, so an untouched form does not light up), and `form.invalid` counts invalid fields in the main form, an `aria-invalid` group or combobox around a field included, omitted when 0. The message, clipped to 120 chars, is the first of: the `aria-errormessage` target, an `aria-describedby` target that looks like an error (`role=alert`, `aria-live`, a class with `error`, `invalid`, `danger` or `feedback`), such error text in the field's own box (its highest ancestor, at most 5 up and below the form, holding no other field, so another field's error never attaches), the native `validationMessage`, then any other describedby text that is not the field's label or placeholder. A visible input that `isTypeahead` accepts, holding typed text, whose own typeahead box (`taRoot`, `taParts` and `isTypeahead` shared with fill through `TA_BOX_LIB`) has an empty hidden input, where a pick lands, gets ` unpicked` (a plain input beside an empty hidden one, with no popup, does not); `form.unpicked` counts them in the main form (omitted when 0), and a required one also counts in `requiredEmpty`, so typed text that was never picked does not read as done. A prefilled hidden input (edit forms), a box shared with another control, or a faded honeypot never does. Hidden rows: a required-empty field of the main form (`reqEmpty`, the same test `requiredEmpty` counts) that `snapVis` drops (`display:none` behind an "Enter manually" button, a faded custom input) gets a row after the ordinary rows, flagged ` hidden`, so `requiredEmpty` never counts a field no row shows; fill it by `ref`. At most 10, under the same role and query filters and `max`. Its name is its label, `nearText` or placeholder, else the label text of its nearest shown section (`sections`: shown ancestors up to 6 levels, stopping at form, main, body or one holding more than 5 fields), else `accName`. `reveal=<ref>` names a shown, enabled, non-submit button in the nearest section that has one (`revealer`): one whose `aria-controls` contains the field first, then a typing name (`REVEAL_TYPING`), then `aria-expanded=false`; a button with no row of its own gets one right after. A trap never gets a row, nor a hidden twin of a shown field (same role and name). An ordinary row that is required-empty and a `honeypot` but not a `decoy` also gains ` hidden` (a clip-hidden input under a visible label). `decoy(el)` is `trapLike(el, labelled)` with `labelled` true when one of `el.labels` is visible: `honeypot(el, labelled)` then skips the pixel and clip tests, so a pixel or clipped input with a visible `<label>` is an sr-only custom input there, not a trap (off-document and `aria-hidden` still are). Fill's `fieldVis` (and so `ident`) passes a narrower `labelled`, `wanted(el)`: the field is `required` or `aria-required`, named by a visible `<label>` or an `aria-labelledby` target with visible text, not `tabindex=-1`, and its label or name doesn't say to leave it blank (`leaveBlank`, shared with `trapLike`). So `fill {label_pattern}` fills a required sr-only input (a "Referral code" styled to a pixel) instead of refusing it as a bot trap, while an unlabelled or optional pixel input is still one.
- **Names:** `labelWords` skips hidden descendants and popups inside a label (`[role=listbox]`, `[class*=dropdown]`, live regions). A field with no label (`labelText`) is named, before its placeholder, by `nearText`: the nearest earlier sibling of it or its 3 nearest ancestors, never past a list item, fieldset or form, and never text beside another control. These flow into `ident()` for every tool.
- **Click by name:** `click {label_pattern}` resolves through `clickableByLabel` (via `resolveClick`), which `CLICK_LIB` ships only to the click, hover and trusted probe scripts; `trusted_probe` uses it when it is not probing for fill. It ranks enabled buttons, links and clickable roles by accessible name (and an input button's value), visible ones first: the whole name, then a match on word boundaries, then any match. A control inside another hit is the one kept. A tie at the best tier refuses with `candidates` rather than guess; a match only on disabled controls names them. A resolved target (by `ref`, `selector` or name; `trusted` too, before any mouse event) whose button, input, select or textarea is natively disabled, `disabled` itself or inside a `fieldset[disabled]` outside that fieldset's first `<legend>` (an inner node refers to its disabled button), is refused as `{ok:false, el}` with `... is disabled; nothing was clicked`, since the browser drops the click; `aria-disabled=true` still clicks, as such forms show their errors on click; no match lists up to 8 visible names. Open shadow roots are searched only when the light DOM has no enabled match.
- **Select:** `select` reads options only from the target control's own list: its `aria-controls`/`aria-owns` targets (react-select's listbox id derives from its input id; Downshift and Radix popovers link that way), else a list in a wrapper holding no other control, else options that appeared after select opened it (their popper wrapper, cmdk root or dialog then supplies the search box). A bare input's box is its parent, unless that parent is the page's: `<body>` or `<html>`, one containing the list the input (or its inner input) names by `aria-controls`, or one holding two or more other fields (`input` not hidden, `select`, `textarea`), as a page-wide `<form>` or `<main>` does; the input is then its own box. A page-level box made every list in it the control's own part, so a listbox it named was skipped and an ignored pick read as an empty list, and its text could be read back as the pick. One helper (`ctlBox`, in `SELECT_OWN_LIB`) makes that choice at the start and again in `select_read` for a control the page replaced on pick, so a re-rendered empty input is never read through its form's or body's text; a control that was its own box at the start stays its own box, since the new node may have dropped the `aria-controls` that kept its list-holding wrapper out. A search box is only the popup's own and empty: a `[cmdk-input]`, an input inside a Radix popper wrapper or cmdk root, or a `combobox`/`searchbox` input whose `aria-controls` names the list select is picking from (one of the control's linked lists, or the list holding the options it found); never another field of a form dialog, a combobox naming its own list included, which is never focused or typed into. `[cmdk-item]` counts as an option; a disabled one (`aria-disabled=true`, or `data-disabled` bare or `true`, since cmdk writes `false` on enabled items) is never pressed or listed, and a match only there misses with an error naming it: at once when it is exact or there is no search box, else only after a typed filter turns up no enabled match. An option the control already shows as chosen (on a multi-select, which shows two or more chips (a class word `badge`, `chip`, `tag` or `multi-value`, split at `-`, `_` and camelCase), several value elements alike in tag and class, or has `aria-multiselectable` on the control or list: an element's own text in the box or a comma part of its text; a label, whose text ends in `:` or equals the control's label, is never a value; on a single select: the box's whole text or one element's own text, so `Paris` is not chosen when it shows `Paris, Texas`; never a placeholder; or the option's `aria-checked`/`data-state=checked`) is not pressed again, since cmdk pickers toggle, and the result carries a `note`. After a pick, a popup select opened that is still open (a multi-select) gets Escape inside it, at the focused element there, else its search box, else the control; a popup that was already open stays open. A miss sends that Escape only while the popup is open, since Escape on a closed Downshift menu clears its selection. A refusal changes nothing on the page beyond undoing select's own typing and closing its own popup with Escape. A control inside an open modal (`aria-modal=true`, or a `<dialog open>`) that is not the control's own popup gets no Escape inside the dialog, since the page's close-on-Escape handler, on the dialog or on the document, would close the whole dialog and the form with it (`escapeOwn`, `modalOf`): select presses again what it pressed to open the popup (a toggle), and only if the control still reads open sends Escape to the popup's focused element or own list when that sits outside the dialog; a list inside the dialog is left open (`open: true`). A dialog that closed anyway (a document-level handler hears any Escape) is reported on the answer (`dialogClosed: true`). It takes select's typed filter back out and puts back the input's prior value and its hidden companion (`untype`, `UNTYPE_LIB`); after a press (a refused final read) only while the typed box still holds exactly what select typed and the companion what it held right after that typing, so a value the page's pick wrote (in its own format, companion and all) stays. A miss pressed no option and also restores what opening the control cleared, as it always did. A list the undo reopened after the Escape closed it gets Escape again. Nothing is blurred, the control or its popup search box alike: a widget that commits its first option on blur (MUI `autoSelect`, select-first-on-blur) would pick after `ok:false` from whatever the list shows. A popup select opened that still reads open after the Escape (a widget with no Escape handler; the read judges open as its Escape does) is left open, and the refusal says so (`open: true`, `saysOpen`): a synthetic press outside would fire every outside-click handler on the page, closing a drawer or panel the form sits in, and body click listeners with it. An empty input whose box holds only the control's own label reads as showing nothing, not the label. A popup already open before select pressed anything stays open. A control that shows nothing two polls after its press gets one press on a button whose `aria-controls` names the same list (Downshift's toggle button). The readback joins several shown parts (badges) with commas when the box text has none. It verifies a multi-select's pick anywhere in the box text; a single select's only when the whole shown value or one element's own text equals it (a label beside the value in the trigger) or shows it in the control's own format, or when the value grew from the prior one by a comma part or element equal to it (a multi-select without chips). The control's own format is the option's text followed by a separator and detail (`Cherry (cherry)`, `Blue - #00f`, `Blue · primary`, `Blue [BLU]`, `Blue: primary`; a plain space and another word is not one), or the option's `value` or `data-value` attribute; `select_pick` keeps the list's other option texts at the pick (`s.others`), and text that one of them longer than the pick equals or starts is never the pick, so pressed `Blue` beside `Blueberry` and `Blue Jay` is refused when the control shows `Blue Jay` or `Blue Jay (bj)`. **Tab indices are positional.** `tabIndex` is the tab's current position; opening or closing tabs shifts it. **Tab creation.** `new_tab` defaults to the browser in use (`defaultBrowser`: topmost on screen, else the system default browser if it runs, else any running one) and requires a running browser with an existing window. It never calls `activate()` and never changes which tab a window shows: it reads the shown tab first (Chrome `activeTabIndex`, Arc `activeTab.id()`, Safari `currentTab.index()`) and puts it back if the browser switched to the new tab (live, Canary did). That costs at most 3 Apple Events. **Clicks that open a tab.** A popup blocker drops a synthetic click's new tab silently, and an allowed one appears where the caller must hunt for it, so `click` reports both. The click page script's first pass (`probe`) stops before clicking an element whose default opens a new tab (`blankHref`: a link, or a form's submit button, aimed at `_blank` with an http(s) URL), keeps a closure over it on `window.__perch_blank` under an owner token and returns `{blank:{href}, tok}`; a probe that finds another call's closure still waiting (under 10s old) clicks nothing, marks the slot a clash, which that call's second pass also refuses, and both answer `ok:false` mid-click, while the second pass answers the kept token and `clickBlank` refuses one that isn't its own (not verified, no `opened`) or that names its own element already run by another call (a spent slot keeps `done:tok`); anything else clicks in that same call, so an ordinary click costs what it did (one event on a quick target) and sends only the prelude, `CLICK_LIB`, `BLANK_LIB` and the click body (readback code only with `readback`), about 19KB where it was 50KB. For a candidate the runtime (`clickBlank`) reads every window's tabs in one bulk event (`windows.tabs.id()`; Safari `windows.tabs.url()`), so a tab the browser put in another window (links set to open in windows, a popup window) counts too, sends the second pass (`CLICK_BLANK_GO`, a short script that runs the kept closure), which clicks the kept element (a page that changed in between refuses), and reads again, every 100ms for up to 500ms while nothing is new. During every click, `watchOpen` wraps `window.open` for the synchronous `el.click()` only and puts it back (unless the page replaced it meanwhile): a null return is `blocked` with its URL, a window is `opened:{url}` plus `note: "list_tabs to find it"`. **Screenshots.**
- **Capture:** the runtime entry `shot` reads a window's own pixels regardless of z-order. It checks the grant with `CGPreflightScreenCaptureAccess` (never prompts); without it every screenshot, plain or element, is refused before anything is spawned, `screenshot: needs the Screen Recording grant for the app running perch (System Settings > Privacy & Security > Screen Recording); nothing was captured`: the daemon is an `osascript` child of the Node server, so a Node `screencapture` has the same responsible process and no grant either, and would raise the grant prompt (which takes key focus) or return wallpaper or a bare frame. With the grant the **capture helper** takes the shot first, and `screencapture` when it can't.
- **Capture helper:** a second `osascript` the daemon launches (`helperUp`: `/usr/bin/osascript -l JavaScript -e` with this same runtime's source, running `__perch.shotHelper(prefix, daemonPid)`) captures in process with `CGWindowListCreateImage` (`IncludingWindow`, `BoundsIgnoreFraming`, so no shadow) and crops, scales and encodes it with `encodeShot`, the code the `screencapture` path uses: a crop before any downscale, a `CGBitmapContext` downscale only when wider than `maxWidth`, `NSBitmapImageRep` PNG or JPEG at 0.8. Requests and replies are files: the daemon writes the request as JSON to `<prefix>.req` (atomically), the helper polls for it (with `access(2)`, cheaper than `fileExistsAtPath`'s bridge) and for its parent every 10ms (`HELPER_POLL_SECS`), removes it, and writes the reply (`{data, image, clip?, cut?}` or `{noImage}`) to `<out>.w`, renamed to `<out>` so a reply file is always whole; the daemon polls for it every 2ms and removes it and any `.w` on every path. Measured live on Canary (626x1074pt window at 2x, 12-run p50 through `handleCall`): PNG 187 -> 97-100ms, JPEG 198 -> 88-91ms (85ms with the helper polling every 2ms), an element crop 143 -> 131ms (the `screencapture` crop already overlapped the Accessibility walk). In process the image takes 11-15ms warm against `screencapture`'s 140-170ms, and the PNG encode about 30ms (JPEG 4ms). The helper exists because `CGWindowListCreateImage` is proxied through `replayd` (since macOS 15), which serves one live process per executable: while one `osascript` that has captured is alive, another `osascript`'s capture waits the proxy's 30s and gets no image, and, found live on macOS 27.2, the one served then stalls too until the other exits; killing the served one does not release the waiting one. A native call holds the JS lock, so no thread of the process making the call can bound it (a JS block on an `NSThread` blocks the main thread for as long). The daemon therefore never makes the call: it waits `HELPER_WAIT_MS` (1s) for the reply, inside the capture's `SHOT_CAPTURE_SECS`, then kills the helper, leaves it off for `HELPER_STALL_MS` (60s) and takes the shot with `screencapture` in the same call. Live, with a foreign `osascript` holding `replayd`, the first screenshot took 1.5s (daemon start included) and the rest `screencapture`'s time, none failed. One helper per user: it holds an `flock` on `$TMPDIR/perch-capture.lock` (a 0-byte file left in place) for its life; the daemon probes the lock (`LOCK_EX|LOCK_NB`, then `LOCK_UN`) before launching one, and a lock held (another perch server's helper) sends every shot to `screencapture` for `HELPER_LOCKED_MS` (10s) before it probes again. A helper that ends without having answered (it lost the lock, or never ran) is left off for 5s. It exits 30s after its last shot (`HELPER_IDLE_MS`) or once its daemon is gone (`getppid`), so it holds `replayd` only while shots come; while it does, another tool's in-process `osascript` capture waits its 30s (as it did before `screencapture`, when every daemon captured in process). `PERCH_CAPTURE_HELPER=0` in the server's environment turns the helper off (Node sends `noHelper`, and no lock is probed or helper launched), so every shot takes `screencapture`, for a machine where another tool captures in process. Before launching, the daemon removes any `<prefix>.req` an earlier daemon with the same pid left. `NSTask` reaps an exited helper (checked live: no zombie after its idle exit). Idle, polling costs the helper about 2.5% of a core (live, `ps` cputime over 4s and 20s windows; a bare JXA `delay(0.01)` loop costs about 1.5%), against 9% at the earlier 2ms poll and 4.25% at 10ms with `fileExistsAtPath`; the parent is read every poll (about 0.2% more), since a helper left behind by an exited daemon holds the lock and sends a new daemon's shots to `screencapture` for 10s; it can't block instead, because the only wake-ups JXA offers cleanly are pipes, and a daemon write into a pipe whose helper died is a SIGPIPE that kills the daemon (`fcntl` `F_SETNOSIGPIPE` and `signal(SIGPIPE, SIG_IGN)` can't be bound from JXA). Live, two perch servers capturing concurrently (12 shots each): both finished every shot, the one with the helper at p50 115ms, the other through `screencapture` at 217ms, no shot over 0.63s (the first, daemon start included).
- **screencapture:** `/usr/sbin/screencapture -l <CGWindowID> -x -o -r -t tiff` as an `NSTask` into a temp file (removed after), polled every 2ms, loaded with `NSBitmapImageRep`, then `encodeShot`. An uncompressed TIFF is written about 40-60ms sooner than a PNG screencapture would compress only for perch to decode again; its pixels match the PNG's once color-managed, though it carries the display's own profile ("Color LCD") where the PNG was tagged Display P3. A plain PNG shot that needs no downscale (`maxWidth` 0, or the window's width times the densest screen's backing scale within it) is taken with `-t png` and returned as the file's own bytes, never decoded or encoded again; one that still comes back wider is scaled as usual. JPEG never uses screencapture's own JPEG, whose quality is not 0.8. `screencapture` exits after each shot, so it never holds the proxy and is never blocked by a holder, even four at once. One that gives no image within the capture's 3s (`SHOT_CAPTURE_SECS`, counted from before the helper's wait) is terminated (SIGKILL if it outlives SIGTERM by 200ms, then its file is removed, so no capture is left in `$TMPDIR`) and the call refused with `timeout: screenshot: the window capture gave no image within 3s; nothing was captured`, after the crop's restore, with the restore's `; the scroll may be left moved ...` when it got no answer. A run that ends without an image (nonzero exit, a file that won't load or has no pixels) is run once more, in a new temp file, inside the same 3s, so the retry never lengthens the worst case and a run killed at the deadline is never retried; a second miss is the fallback or refusal below. Live, 1 in 30 crops missed once with two perch servers alternating on one window; `screencapture` itself exits 1 with no file for a window id that is gone, but 120 overlapping runs from two `osascript` processes on one window (and 120 from three shells) all gave an image, so no lock serializes the runs.
- **Fallback:** only with the grant, when the helper gave no image and both of the runtime's `screencapture` runs fail (nonzero exit, a file that won't load, a failed launch, crop or downscale; its file is removed either way), Node spawns `screencapture -l <CGWindowID> -t png|jpg` into `perch-<pid>-<seq>-<time>` temp names (the counter keeps two calls in one millisecond apart) and `sips` when the image is wider than `maxWidth`; dimensions come from the PNG/JPEG header (`imageDims`). Each child is SIGKILLed at 3s (`shotChild`): a killed capture is the runtime's coded `timeout`, one that exits nonzero, writes nothing or writes no PNG/JPEG is `window_offscreen` (the window is not resolved again), a failed crop is a coded `could not place the element`, a failed downscale sends the full-size image. No execFile or fs message or temp path reaches the caller, and every temp file is removed.
- **Missing CGWindowID:** minimized windows and windows on another Space cannot be captured; perch refuses instead of returning another app's pixels.
- **Tab targeting:** only the active tab of a window is rendered. A background screenshot refuses an inactive `tabId` or `tabIndex`; `raise:true` is required to select it.
- **Element crop:** `screenshot {ref|selector}` needs Accessibility: without the grant it refuses before any page JS (`screenshot: cropping to an element needs the Accessibility grant ...`), since only the Accessibility page area places the viewport in the window; the page's `screenX` and outer size can't tell browser chrome from DevTools docked right or bottom or a side panel, so an estimate from them would crop other content silently. It then runs `shot_clip` (an element larger than the viewport is refused before anything scrolls, `screenshot: the element is larger than the viewport (WxH CSS px in IWxIH) ...`; every ancestor's and the window's scroll position is kept on `window.__perch_shot` under a token `shot_clip` makes in the page (a per-page counter and a random suffix, so its source carries no per-call value beyond `A`) and returns; the element always gets `scrollIntoView({block:"nearest", inline:"nearest"})`, a no-op when it is fully visible, and `moved` compares those scroll positions before and after; an ancestor other than `html`/`body` whose overflow is not visible and whose client area still cuts the element's rect by more than 1px refuses the crop, `screenshot: the element is clipped by a scrolling container; nothing was captured`, since the viewport would show that container's other content; else its client rect, the viewport and the token), the capture (the helper's, sent once the map is known, the helper launched before the walk when it isn't up; without the helper, for an element that did not move, a `screencapture` run started before the Accessibility walk and overlapping it, which a refusal from the walk stops, removing its file), and `shot_restore` in one runtime call, and restores whatever the capture did. Every exit of `shot_clip` that captures nothing (that refusal, the hidden document below, a throw after the record) puts the scroll back in the page itself and drops its record, so the runtime restores only after an `ok:true` clip or a clip whose reply never came. The record is exclusive per tab (the tab lock is per server): `shot_clip` first finds any record under 10s old (its `at`) another call's, and refuses before it resolves or scrolls anything, `screenshot: another perch call on this tab is mid-screenshot; nothing was scrolled or captured, retry` (`SHOT_BUSY`); an older one (a crop cut off before its restore) is put back with `scrollBack` (`SCROLL_LIB`, shared with the typeahead fill) once the element is known to fit, then replaced, so the user's scroll from before it returns. `shot_restore` (fixed source) puts back the current record and returns its token; one that is not this call's, none after an `ok:true` clip, or a restore that got no reply adds `; the scroll may be left moved (its restore got no answer)` to the refusal or timeout, or becomes the capture's `warning`, except that a capture whose restore found another call's token is refused (`screenshot: another perch call on this tab took over this screenshot's scroll record, ...`) instead of returned with a warning. A record another perch server left is never restored for this call's fault before the clip records, and never read as its paint proof. Every page call is bounded where the tab is pinned (`pollExec`, Chromium by id, one instance): the clip and the restore 1s each, each paint poll 0.5s, and the clip, the Accessibility walk (which stops unplaced past the deadline) and the paint polls share a 3s budget (`SHOT_BUDGET_MS`); a clip whose reply never came is restored and refused with `timeout: screenshot: page JS got no reply within 1s; nothing was captured`, and paint polls none of which answered with `... within 3s ...`, both after the restore, so with the capture's own 3s (plus up to 0.4s to stop a hung run) a crop ends in about 7.5s at worst instead of the lane's 30s with the page left scrolled. The capture itself is bounded at 3s (see Capture): before that, a second perch server's crop (or plain screenshot) of any window stalled for the lane's 30s in `CGWindowListCreateImage` once another server's REPL had captured, and the lane's kill skipped the restore. Safari, Arc and a browser with a second instance take the plain execute, unbounded as before; one Accessibility read can still take the system's messaging timeout. Nothing runs on a tab its window doesn't show. The Accessibility page area gives the origin and points per CSS px, zoom included (`aim:"ax"`); when none matches the viewport the call is refused after the restore (`screenshot: Accessibility shows no page area matching this tab's viewport ...`). The crop is the element plus 8 CSS px, cut at the viewport, taken before any downscale (`CGImageCreateWithImageInRect`; fallback `sips --cropToHeightWidth --cropOffset`, which only an element that did not move may take: Node's `screencapture` runs after the restore, so an element `shot_clip` had to scroll to is refused with `screenshot: the window capture gave no image; nothing was captured` when neither run gave a usable image; without the grant any crop gets the grant refusal above); `meta.clip` is that rect in capture pixels, `clipped:true` when the element itself was cut. An element `shot_clip` scrolled is captured only once the page proves the scroll painted: a hidden document (a covered or minimized window paints nothing) is refused for the restore, and a visible one arms a double `requestAnimationFrame`, plus a 100ms timer that marks the record `late` if the frames have not come by then (a window the browser stopped painting whose `visibilityState` still reads visible), and the fixed-source `shot_painted` polls up to 6 x 50ms before the capture, reading `{painted, late, token}` of the current record: painted with this call's token proves it; `late`, another call's token or no record refuses at once with `screenshot: the window isn't painting (covered or hidden); ...; nothing was captured`, as do 6 polls without proof; an element that did not move takes no poll. Every refusal is just `{ok:false, error}`, with none of the window's geometry. Since it runs page JS, the dialog watchdog covers it and it takes the tab lock.

**File upload.** `file_upload` reads the file in Node and ships it base64 in one page call, where a `DataTransfer` sets the input's `files` (about 80 KB across the bridge, nothing in the agent's context). It stats the file first and refuses one over 25MB, or over 700KB without the daemon: a one-shot osascript takes the script as an argument, and base64 of 700KB is near the ~1MB argument limit. The 25MB cap is a guess, not yet tuned live. Rejected: the OS file dialog (takes the foreground) and a localhost server the page fetches from (Chrome's local-network prompt). Unverified on real sites: uploads a site sends asynchronously after `change`, which the result can't see.

**Drop zones.** A `file_upload` target that is not a file input (a `selector`/`ref` on a div, or a `label_pattern` that names no file input's label and matches exactly one visible element's text or `aria-label`) is a drop zone. Its file input, if any (one inside it, else the only one within 3 ancestors), still comes first by the usual accept/name rules. With no input, the page script dispatches `dragenter`, `dragover`, `drop` on the zone carrying a `DataTransfer` with the file (a `DragEvent` where the engine takes `dataTransfer` in its init, else an `Event` with it pinned on). A hidden input that no form would submit (no `name` or no `form`) is watched by a MutationObserver through `change`; if the file name never shows, nothing on the page mutates (other than the input) and no new fetch/XHR resource timing entry completes (counted from before the file was set) within the 1s `file_upload_shown` poll, Node runs `file_upload_drop`, which empties the input and drops on the zone (the one given, else the input's nearest visible ancestor within 3 levels). Any mutation or request counts as handled, so a busy page falls back to the old input-only result rather than risk a second upload. So does a change handler the eval can read (`onchange`, React's `__reactProps$`/`__reactEventHandlers$` `onChange`, Vue's `_vei`), which skips the watch; Chrome's isolated world sees none of them, so there only requests and mutations tell a wired input (react-dropzone's own input, whose handler may change nothing within the wait) from an unwired one. A drop is `{dropped:true, el:<zone>}` and counts only when a file input other than the emptied one holds the file or the name appears more often than before the call, polled for 1s; otherwise `{ok:false, dropped:true, error}`. State between those calls lives on `window.__perch_up`, which each `file_upload` replaces. Another perch server can upload on the same tab, so the state carries its call's key (ref, selector, label_pattern, file name; `UPLOAD_OWN_LIB`) and an owner token (`rbTok`), and the unwired first pass returns that token. A `file_upload` that finds another call's state still waiting for its drop, under 10s old, refuses before setting anything (`another perch call on this tab is mid-upload; nothing was set, retry`); an older one counts as abandoned and is replaced. `file_upload_shown {up}` and `file_upload_drop` answer `{lost, tok}` for another call's state before disconnecting, emptying or dropping anything; the up poll answers `{tok}` while not seen, and the runtime `wait` given a `tok` keeps polling only while the answer carries that token. A lost state or another token (two servers with identical args) ends the call with `UPLOAD_TAKEN` (`{ok:false}`, the file set on the input, no drop). The drop marks the state done rather than clearing it, since the verifying poll still reads it; a second drop on a done state is another call's and answers `lost`. A missing state on a document that has made tokens (`window.__perch_tok_n`) reads as lost; on a fresh document the drop still says the zone left the page. Unverified on real sites: react-dropzone and friends in Chrome, Safari and Arc (whether a synthetic `DragEvent`'s `dataTransfer` sticks, and zones that check `isTrusted`).

**Trusted input.** `click {trusted:true}` and `fill {trusted:true}` default to background routes that do not explicitly activate the browser or move the cursor. Background fill directly uses Chrome's editing command in the targeted tab; the live scratch-page test verified a trusted input event and exact Unicode value in an inactive tab while its window was minimized, with no Canary key focus during continuous monitoring. Background SkyLight click needs an on-screen window and its active tab; its event did not reach a minimized window in the live probe. `raise:true` keeps the foreground HID route; its fill passes only when the field holds the exact text (whitespace runs and CRLF normalised, or a phone mask's digits), and a miss reports what the field holds, never the text sent.

1. For clicks and raised input, `trustedTarget` resolves the browser, checks Accessibility with `AXIsProcessTrusted()` (which does not prompt), and gets the target pid, CGWindowID, and frame from `procs()` / `ids()`. With `raise:true`, `focus` pins the window by id before raising it, since `windows[i]` is positional. Default trusted fill uses page JS and needs no CGWindowID or Accessibility grant.
2. `skyInit` binds SkyLight event functions in JXA. The background route never posts `SLPSPostEventRecordTo` AppKit focus records: they made input reach Chrome but redirected the user's keyboard until the restore.
3. Background trusted clicks require the target tab to already be active in an on-screen browser window; they never switch tabs. With `raise:true`, `aim` selects the target tab. A hidden tab's `screenX` and `outerWidth` are stale, so `trusted_probe` retries until visible, scrolls the element into view, estimates the screen point, and arms event recorders. The estimate puts all horizontal chrome left of the page and ignores zoom, so `aim` corrects it: background clicks read the page's web area from the Accessibility tree (`axPageArea`: the `AXWebArea` whose shape matches the viewport, since a side panel is a web area too; its width over `innerWidth` is the zoom), because directed SkyLight moves never reached a background page live. The foreground HID path calibrates from a posted mouse move and falls back to the Accessibility tree. Results carry `aim` (`ax` or `mouse`) and a `calibration` trace. The estimate alone never clicks: the hit test below needs the page area, so without one the click is refused.
4. Background mouse events use `SLEventPostToPid` with target pid/window routing fields and `CGEventSetWindowLocation` set to the **window-local** point. The sequence includes a move primer and an off-screen click pair before the target pair. A Command flag on the down event lets WindowServer deliver to the background window; the up event has no Command flag, and Chrome receives an ordinary trusted click with `metaKey: false`. Passing a screen point to `CGEventSetWindowLocation` shifted the live Chrome click by the window's y-origin; the local point landed at the exact element center. Background fill instead uses `document.execCommand('insertText')` directly on the requested tab's field, including inactive or minimized Chrome tabs. It verifies the trusted event and exact value. The `raise:true` path uses `CGEventPost(kCGHIDEventTap)` for the click and the session tap for typing, then restores the cursor. `trusted_check` reports `hit` for routed clicks. A click by point proves delivery the same way: `trusted_frames` arms a recorder for the first trusted mousedown (and the element it landed on), and a click the page never received is `{ok:false, hit:false}`, never retried or activated; a check that finds no recorder (the page navigated) keeps `ok:true` with a `note`.

A trusted click posts only where the page itself is, since frames take only an `fN` ref (see Frames). The page checks come first and are cheap: `trusted_probe` refuses an element that is, or lies inside, an IFRAME, FRAME, OBJECT or EMBED before scrolling it, and one whose aim point `elementFromPoint` finds on or inside such an element (a wrapper or overlay with a frame over its center), before arming anything. A click by point has no element, so its first page call, `trusted_frames`, returns the frames' viewport rects (open shadow roots included); `pointOnFrame` places the point through `axPageArea`, else the page's origin estimate, and refuses a point inside any rect. A page that can't answer fails closed. Page JS can't see a frame inside a closed shadow root, and `elementFromPoint` returns the shadow host for any hit inside a shadow tree, so the last word is Accessibility's: `offPage` hit-tests the final screen point (`AXUIElementCopyElementAtPosition` on the browser's application element, bound in `axInit`) and walks `AXParent` from the hit (64 steps) to the first `AXWebArea`, which must be the page's own (`axPageArea`'s element, compared with `CFEqual`, else by frame within 1pt when `CFEqual` can't bind). Another web area first is an embedded frame, however it got there; none at all is browser UI, a bubble or a child window (a JS dialog). Those, a failed or unbound hit test, and no page area all refuse with nothing posted: "the point is not on the page itself (embedded frame or browser UI); ...". It runs for every trusted page click (selector, ref, x/y, background or raised, and `select {trusted}`'s) and for raised trusted fill's click, after `aim` fixes the point and before `arm` and any post. It costs AX reads only (about 4, plus the page area aim usually already read), no Apple Events (`test/perf-budget.test.mjs`). The hit test is application-scoped, so another app's window over the point does not count (the background route delivers to the pid and window anyway), but another window of the same browser over it does, and refuses. Everything runs after `trustedTarget`, so `raise:true` has already raised the window when it refuses: the point is only known once the tab is shown and, in the foreground, calibrated, and a hit test only means something on an on-screen window. Raised fill's probe clears the field before these checks, so a refused raised fill can leave it empty.

The earlier bare `CGEventPostToPid` / `SLEventPostToPid` delivery probes did not reach Chrome's page. The routed SkyLight sequence is a separate path. `skyClick` and `mouse` both reject a target point outside the window frame.

**Trusted press.** `press {trusted:true}` is for widgets that ignore synthetic keys (they check `isTrusted`, or rely on native defaults such as Tab focus, Enter in a combobox picker, Escape closing a native popup). `skyKey` posts a keyDown/keyUp pair with `SLEventPostToPid` to the browser pid only: no window fields, no Command flag (shift, 0x20000, is the only flag), and the key's Unicode string on both events (`\r`, `\u001b`, `\t`, `\u007f`, NS function-key characters for arrows, Home/End, PageUp/PageDown, forward Delete, F-keys). Only named keys are accepted; cmd/ctrl/alt chords are refused because real ones can fire browser menu shortcuts, and single characters stay with `fill`. The browser performs the key's real default, so nothing is emulated. `trusted_key_arm` focuses the element and records the first keydown and keyup on window; `trusted_key_check` is polled for up to 1s and gives `hit` (true: a trusted keydown with that key; false: untrusted or another key; null: none arrived). The key goes to the browser's key window and its focused element (live, with focus in the address bar Enter reloaded the tab), so before arming anything `keyFocusMiss` checks with Accessibility alone (no Apple Events): the pid's `AXFocusedWindow` must match, within 4px, exactly one of the pid's CG windows (`procs().byPid`) and that one must be the target's CGWindowID, and an `AXParent` walk (64 steps) from `AXFocusedUIElement` must reach the page's web area (`axPageArea`, matched by frame). Another key window, an ambiguous match, focus in the toolbar, a popup, a side panel or a bubble's window is `tab_not_visible` with a hint: a background trusted click on the page moves focus back into it, and another key window needs `click {trusted, raise}`. The walk stops at the first web area: when that is an embedded frame's (a captcha, a sign-in widget) the press is refused, since frames take only `click {trusted:true}`; `trusted_key_arm` likewise refuses an IFRAME, FRAME, OBJECT or EMBED as the element or as `document.activeElement`. Should the key still miss, `hit:null` carries an error. Also `trusted_key_arm` refuses a Tab from the page's last focusable element (shift+Tab: the first), which would move focus into the toolbar. Like the click it needs the tab its window shows; in the lab, keys reached a covered window but not a minimized one. Live-proven in the lab on Chrome Canary; Safari and Arc are unverified.
The background `mousedown` carries `metaKey: true` because of the WindowServer routing flag, while the resulting Chrome `click` carries `metaKey: false`. Pages that inspect modifiers on `mousedown` may behave differently; verify the resulting page state after critical actions.

Foreground typing creates keyboard events with virtual key 0 and text attached via `CGEventKeyboardSetUnicodeString`, then posts at the session tap. Chunks are split in Node (`chunkUtf16`: at most 20 UTF-16 units, never splitting a surrogate pair). Two traps, both of which make Chrome type "a" (key 0) instead of the text:
- the encoding is `NSUTF16LittleEndianStringEncoding` = `0x94000100`, not `0x14000100` (which yields nil data);
- the stock JXA signature of `CGEventKeyboardSetUnicodeString` rejects NSData bytes as `UniChar*`, so it is rebound with `void *` parameters.

Mouse event fields use raw indices, because `$.kCG*` constants aren't reliably bridged: 1 = click state, 11 = pressure (double).

`scripts/skylight-probe.js` proves SkyLight functions bind from pure JXA. `ObjC.bindFunction` registers the function on `$` (call `$.SLEventPostToPid(...)`) rather than returning it.

**Frames.** Page JS can't see into cross-origin iframes, so `accessibility_snapshot {frames:true}` reads them from the Accessibility tree. The runtime entry `snapshotFrames` runs the snapshot page script (which then also returns `innerWidth`/`innerHeight`, dropped from the header in Node) and walks in the same call. `axPageArea` picks the page's web area (it also returns the element), and a BFS bounded by node count (3000) and time (150ms) emits controls only inside nested `AXWebArea` nodes, so page-level controls stay with the page rows. Each row reads `AXRole`, `AXTitle`/`AXDescription`, `AXEnabled`, `AXExpanded`, the frame's `AXURL`, and `AXValue` only for a checkbox or radio's state. It never reads a field's value, and a secure field gets a `secure` flag so it can be handed to the user. A row whose center lies outside the window, the page area or its frame gets `offscreen`. Node formats rows as `fN role "name" frame="<host>" flags` (`role`, `query` and `max` apply) and keeps them in `frameRefs`, keyed by the handle the runtime resolved and replaced on that tab's next snapshot. They live in Node because the page can't see them and the REPLs respawn. `click {ref:"fN", trusted:true}` sends the ref's rows to `frameClick`, which keeps the row stored under the tab it resolves, walks again and matches by (frame URL, role, name, ordinal among equal role and name in that frame). It then clicks the fresh center through `skyClick` (`raise:true`: `leftClick`, cursor restored), never a stored point. A missing row, a changed frame URL or a changed page URL is the stale-ref error; an `offscreen` row is `{ok:false}`. Sign-in and challenge frames (`handoffFrame`: a short fixed host list, plus `/recaptcha` paths on google.com, so it needs the full frame URL) get a `handoff` flag, and so, failing closed, does a frame without an http(s) URL (about:blank, srcdoc, no `AXURL`) or one nested under a `handoff` frame (rows carry `up`, the ancestor frame URLs, which the click matches too); and a `handoff` or `secure` row is refused with `{ok:false}` before anything is raised, probed or walked; the runtime checks the stored row again (a ref that names an ordinary row in another tab) and the fresh row for `secure`. The result is `{ok, ref, frame, point, aim:"ax", delivery, before, after, hit:null}`: `before`/`after` re-read role, name, checked and `AXFocused` (plus `navigated` or `gone`), since no page recorder can confirm delivery; `after` is re-read every 50ms for up to 0.5s until something besides focus changes, because Accessibility trails the page. `checked` is null when `AXValue` isn't a boolean or number. Every other use of an `fN` ref (untrusted click, fill, press, select, get_text, file_upload) throws `frame refs need click {trusted:true}`. The walk fails closed with the trusted click's codes, but inside the header: without Accessibility, off the tab its window shows (`tab_not_visible`) or without a CGWindowID (`window_offscreen`), the page rows still return with `frames:{error}`; any other failure of the walk (a raw bridge or AppleScript error) is coded by `codeFrameError`: `codeOsaError`'s codes, else `frames_unreadable`, never the raw message. Rows of a same-origin frame the page walk already listed are dropped: with `frames:true` the page script also returns the content boxes of the walked frames (`fr`, dropped from the header in Node like `iw`/`ih`), `snapshotFrames` places them on screen through the page area and its zoom (`frameWalk` returns that area), and a row whose own (innermost) frame's box lies within 2pt of one is left out, so such a frame's controls appear once, as refs that take plain input. A frame nested inside a walked one that page JS did not walk (cross-origin, too small, past 3 deep or cut by the cap) has no box in `fr`, so its rows stay. A frame counts as walked only when `max` left all its rows listed: a page cut before or inside a same-origin frame leaves it out of `fr`, so its controls come back as `fN` rows rather than vanishing from both (a partly listed frame shows its listed controls twice, once per kind of ref). A default snapshot does no Accessibility work (`test/perf-budget.test.mjs`). Live on Chrome Canary (2026-09), with Canary behind another app and a page on 127.0.0.1 embedding a frame from localhost: the frame is a nested `AXWebArea` whose `AXURL` bridges, the button, checkbox and `aria-label`led password field got their names, the password row was flagged `secure` with no value, and trusted clicks on the frame's button and checkbox reached the page (`isTrusted` true; `after` showed the button's new name) with frontmost app, key process and cursor unchanged. A frame URL change made the old ref stale. Chrome gave the checkbox an empty `AXValue` whether checked or not, so its `checked` reads null. A `frames:true` snapshot took p50 162ms against 7ms for the default one (116 against 4 with Canary in front); the walk's own 150ms bound holds it. Links, `raise:true` frame clicks, Safari and Arc are unverified, and so is the hit test against a real challenge widget inside a closed shadow root. Rejected: a configurable hand-off host list.

**Dialogs.** A page's `alert`/`confirm`/`prompt` blocks its JS, so a call that runs page JS (often our own `el.click()` on a confirm button) hangs inside `execute` until the timeout. `rt()` watches every entry except `DIALOG_BLIND` (tab listing, creation, closing, activation, geometry, capture and the dialog entries): after `DIALOG_PROBE_MS` (1500) in flight, and every `DIALOG_REPROBE_MS` (2000) after, a one-shot osascript (never queued behind the hung lane) runs the runtime's `dialogs({target})` with the call's own target (no target: the default target, resolved as the call resolves it). A hit calls `OsaDaemon.abort` with `dialog_open`; the next call respawns the REPL. A call that ends in a timeout is probed once more and the error rewritten, but only when the timeout may be a hang (`hung`, which checks the `HANG` phrases the messages are built from, passed into the runtime so rewording one changes both): the REPL killed (`osascript gave up after`, the only probe with `PERCH_DAEMON=0`) or an execute whose reply never came (`page JS got no reply`, `page JS failed without a reply`, `the <tool> ran but its result got no reply`, navigate's `the page didn't answer`). A `wait`, `wait {quiet}` or `awaitPromise` that ran out while the page answered its polls can't be blocked by a dialog and ends without the probe (a cold one-shot osascript, 0.5-0.8s); when its last poll went unanswered and no run has answered since the poll began or for 1s (`SILENT_MS`), the runtime adds `; the page stopped answering` to the error and it is probed; one reply lost under load after answered runs stays a plain deadline timeout. Dialogs fail closed: perch aborts a call, or answers a dialog, only when it can tie a JS alert/confirm/prompt to the target tab (`ownDialogs`); anything else is ignored by the watchdog (the plain timeout stands) and refused by `press {dialog}`, because answering the user's own dialog in another tab is worse than a refusal.
- **Scan** (`scanDialogs`): Accessibility only, no Apple Events, so a probe with no dialog open costs none (`test/perf-budget.test.mjs`). Live on Chrome Canary a dialog is its own window (subrole `AXUnknown`) holding, two levels down, a group with subrole `AXApplicationDialog`. Browser windows (`AXStandardWindow`) are never searched, because a page's own `role=dialog` maps to that subrole too. Without the grant (`AXIsProcessTrusted`, which never prompts) it finds nothing.
- **Shape whitelist:** structural, never by localized title. An `AXHeading` origin line ("x.test says") plus 1 button and no field (alert), 2 buttons (confirm), or 2 buttons and exactly one plain `AXTextField` (prompt), with only `AXGroup` and `AXStaticText` around them. A secure field, more fields, 0 or 3+ buttons, no heading, any other role (image, link, checkbox, list, pop-up...) or a tree too big for the 300-node walk makes it kind `other`: HTTP sign-in sheets (a credentials hazard), FedCM and passkey prompts, and most permission bubbles. The message is the static texts, or a prompt's field title.
- **Attribution:** Chrome's tab-modal dialog is a child window, and a child window sits directly above its parent in the CGWindowList. So the dialog's CG entry, matched to its AX frame within 4px among the pid's windows of any size (`procs().byPid`), must be followed by the target window's CGWindowID (`ids(t)`), and the target must be the tab its window shows (`isActive`). Ambiguous or missing means not attributed, and so does a target window that another of the browser's windows could be (`ids` marks it `ambiguous`). Apple Events (resolve, the shown tab, geometry) are spent only after the scan finds a candidate. This relies on Chrome answering property reads while a JS dialog is open, which is plausible (it suspends `execute` rather than blocking) but unverified live; if they fail, the dialog stays unattributed.
- **Proof:** a shape and a heading can be mimicked: a permission bubble or the multiple-downloads prompt reads "a.test wants to" over two buttons, the confirm shape. So both `press {dialog}` and the watchdog also need the heading to name the tab's host (case-insensitive, `www.` optional, as a whole host), which rejects "Leave site?" prompts, other origins' dialogs and cross-origin frames' dialogs (the watchdog then leaves the plain timeout), and a hostless page (about:, data:, file:, blob:) is refused. Last, the page must be paused: a JS dialog blocks its tab's JS, the browser's own prompts do not. `pagePaused` runs a no-op through `execWithin` (the bounded NSAppleScript execute, error Ref never read) with a 1s bound; a reply means the page runs, so `press {dialog}` refuses and the watchdog stays quiet. Only a timeout is proof. A fast failure (JavaScript from Apple Events off) or no bounded execute (Safari, Arc) is unproven and fails closed, so dialogs there are neither answered nor reported. The proof costs about 1s, only once a candidate passed the other checks.
- **Answering:** `press {dialog}` needs `target.tabId` (checked in Node and in the runtime), like `close_tab`, so it can never land on whatever tab happens to be in front. Buttons go by position (Enter the last, Escape the first), pressed with `AXPress`; a prompt's text is set as the field's `AXValue` and read back first. It never activates or raises. It polls up to 1s until the pressed dialog's own element stops answering `AXRole`; a dialog the page opens at once, even an identical one, is a new element and comes back as `next` (its kind). A background tab's dialog waits until its tab is shown, so the watchdog cannot see it. The page's own dialogs bring the browser forward by themselves (as `navigate` setting a url did, see Navigation) and take the keyboard (seen live with the browser behind another app: keys the user typed elsewhere landed in a prompt's field); that is the page, not perch, but it is why the live check must run while nobody types. The live check (`scripts/dialog-live.mjs`) targets Chrome Canary on a page it serves on 127.0.0.1, with a second-window case when a second scratch window exists; the attribution rules have not run live yet. Safari's and Arc's dialog trees are unverified. Rejected: auto-dismissing dialogs (a false `ok`), a dialog tool or `click {dialog}` (schema budget), and matching a dialog by browser alone (it answered dialogs in the user's other tabs).

**Navigation.** Live on Chrome Canary (2026-09): `navigate` from a scratch `about:blank` tab to a page served on 127.0.0.1, with Canary behind another app, brought Canary to the front (frontmost app and key process changed, found by checking after each call). `navigate` only sets the tab's `url` and never activates, so Chrome raised itself; a navigation the page started (`location.href` via `eval_js`) did not. Diagnosed live on Canary (2026-09): the raise comes from Chrome's AppleScript `set URL` itself (`t.tab.url = a.url`), which Chrome treats as a browser-initiated typed navigation and brings its window forward for, from an http page as well as from `about:blank`, and on a tab its window doesn't show (it did not select the tab). The bounded NSAppleScript execute alone did not raise, and page-JS `location.href` did not raise in two runs. `new_tab`'s `nt.url = a.url` is the same call, which fits its "may focus the browser" note. So `navigate` now starts the load from page JS: when page JS runs (Chromium, Safari, Arc's shown tab) and the URL is http(s) or `about:blank`, or `file://` from a `file:` page, the stamp call also runs `location.assign(url)`. Setting `url` is the fallback, and on Chromium and Arc (Arc unmeasured, so it fails closed) it runs only when the call passed `raise:true` or the browser is already the frontmost app with the tab's window its front one (`procs()`, `t.w === 0`, no twin instance; checked again with one `windows[0].tabs.byId(id).id()` read right before `url` is set, since the retries can take seconds); otherwise `navigate` refuses before anything loads, naming both opt-ins (`raise:true`, `activate_tab`). A URL that is not absolute http(s), `file://` or `about:blank` (`data:`, `javascript:`, relative, browser pages) never gets that far: `checkUrl` refuses it as `bad_url` in Node, and `loadable` again at the top of the runtime's `navigate` and `newTab`, both before any Apple Event; `test/url-policy.test.mjs` pins the list of places the runtime hands a browser a url. The conditions that reach the fallback: a `file://` URL from a page that is not itself on `file:` (a `file:` page loads another `file://` URL itself, the same stamp, `assign` and arrival proof, so moving between local prototype pages or reloading one stays in the background; live-unverified; a silently dropped load ends as `load_failed`, which then names `raise:true`), page JS can't run (Arc background tab, `arc:` pages from or to; refused up front, `tab_not_visible`; a Chromium tab on the browser's own pages, `chrome:`, `edge:`, `brave:` and the like, read from the url navigate already reads, so no extra Apple Event; refused up front as `tab_not_scriptable`, and with the window in front or `raise:true` the url is set with no page JS on the old page, then the usual load wait), `assign` throws or the page cancels the load (`tab_not_visible`), or the stamp call fails or gets no reply and the load can't be proven started (`timeout`, after the retries below; after a fast failure of the bounded execute the stamp is sent once more, bounded, and only a failure that repeats, such as a handler that didn't compile or JS from Apple Events off, takes the plain path; if that fails too, a bounded `1` probe tells a page that answers or hangs (`timeout`) from one that doesn't run page JS at all (the plain path's error, so JS from Apple Events being off reports itself). The plain path has no Apple Event timeout, so a page that hangs there is ended by the runtime's timeout, coded `timeout`, and a plain `-1712` is reported as `timeout` too). When the recheck right before `url` is set finds the tab's window no longer in front and nothing could have loaded (a url the page can't load, or no page JS), the refusal says so rather than blaming the page. Chromium's own pages running no page JS is assumed, not measured; the PDF viewer shows its document's http(s) url, so it isn't caught up front and gets these fallbacks. The `tab_not_scriptable` advice (instructions, SKILL.md, the error) says to navigate with `raise:true` unless the window is in front. Unmeasured, by the specs: a page's CSP and Trusted Types don't block `location.assign` of an http(s) URL (Trusted Types covers `javascript:` URLs only), so they reach the fallback only through a throw. A same-document `#hash` move is in-page (`same!`). On Safari setting `url` did not raise live, so its fallback is unchanged and carries no `warning`; on Chromium and Arc the fallback returns `warning`. If the reply to the stamp call is lost, a loading tab or a document without the stamp at a different URL counts as started; not when the tab was already loading before the stamp, since an earlier load looks the same. Still unproven, the stamp is sent again with `POLL_EXEC_SECS` and then twice that (within the deadline). The stamp keeps its answer on the page (`window.__perch_navr`, keyed by the call's token), so a retry that reaches the stamped document repeats it instead of loading twice; a retry that reaches a document without it counts as arrived when it shows the URL asked for (unless the tab already showed that URL) or, when the tab wasn't loading before, any other URL (a redirect), and otherwise starts the load itself. The live raise between two 127.0.0.1 pages most likely came this way (not reproduced): `NAV_EXEC_SECS` (0.5s) is short on a loaded machine, and a page that still reports `loading` skips the lost-reply check, so the old fallback set `url`. Residual: a retry on a fresh document at the same URL as before (a reload navigate) or on a redirect while the tab was already loading can't tell a committed load from none and loads once more, from page JS. A page-started load is not a typed one: the old page is the referrer, `beforeunload` can run (and show its dialog if the user interacted with the page), and the page's own rules (sandbox, CSP) apply. The page can cancel it: a Navigation API `navigate` listener that calls `preventDefault` is seen by the stamp call, and `navigate` refuses (or, with `raise:true`, sets `url` with the `warning`); a load dropped any other way (the user stays on a `beforeunload` dialog) looks like a download or 204, so once `loading` settles with the tab's URL unchanged `navigate` does not load it again and returns `{ok:false, error: "load_failed: the tab stayed on <url>, ..."}`, unless the URL asked for is the one the tab had (a reload, still `ok:true, waited:false`). The load check reads `location.href` and `location.protocol` in the same execute, so no extra Apple Event: `url` is the committed document's URL, with `requested` added when it differs (a redirect, compared after URL parsing), and a document on `chrome-error:` (Chrome's network error page, assumed from Chromium's source, not yet measured live) or `safari-resource:` (Safari's, assumed, not measured) is `load_failed: <url> did not load`. When loading settles with the tab on another URL and no check proved a new document (none answered, or the last one found the stamped document), one more bounded execute (`NAV_EXEC_SECS`) decides, as at the deadline below: the stamped document answering is the coded timeout (its message gives the time spent), an error page is `load_failed`, and no reply (a page Chromium won't script, such as its error page if it runs no page JS) or a new document is `ok` with that URL, `waited:true` only if the new document answered complete. So an error page that runs no page JS is no longer reported as a finished wait; whether Chromium's error page runs page JS is still unmeasured. The check also says whether the stamped document is still there (`old`), so the deadline no longer answers `ok:true` for a load that never committed (Safari has no idle rule, so a download, 204 or dropped load there used to wait 15s and claim `ok`): when the last answered check saw the old document, one `url` read and (not on Safari, which has no `loading`) one `loading` read, made only then, decide. The tab still on that url is `load_failed: the tab stayed on <url>` only once it has settled; still loading, it is the coded timeout. A tab on another url that has settled, or (on Chromium, for a page-started load) still loading on the URL asked for, is checked once more with one bounded execute (`NAV_EXEC_SECS`), since live Canary (2026-09) shows a page-started load's pending url while the old document still answers: the stamped document answering is the coded timeout, and no reply or a new document means the load committed after the last answer, `ok:true, waited:false` with that url (`waited:true` if the new document is complete, `load_failed` on an error page). Otherwise it is `timeout: <url> had not committed after 15000ms; the tab shows <u>; it may still load, check before retrying` (Safari may show a pending url, so it always lands here). A new document that committed but isn't complete, or no check ever answered, is still `ok:true, waited:false` with the URL asked for. A raised background Arc tab (no page JS) reads its `url` before the set, then polls `loading` every 50ms with the idle rule and reads `url` once it settles (or at the deadline): moved is `ok` with that URL; unchanged is `load_failed`, but only once `loading` has read true or `ARC_START_GRACE` (1500ms, provisional until `scripts/navigate-live.mjs` measures Arc's start lag) has passed, since Arc can read not loading for a while after the set. At the deadline a moved url counts as committed (`ok, waited:false`) only when the last `loading` read was false: Chromium shows a pending url while the old document still answers, so a moved url still loading, or with every `loading` read failed, is the coded timeout, as is an unmoved one; an unreadable `url` (a fresh tab) keeps `ok, waited:false`. These are property reads: nothing is activated, selected or raised. An Arc tab still on `arc:` when the deadline hits is `load_failed` (going to an `arc:` URL stays `ok, waited:false`). The stamp call's same-document check uses the page's global `URL`, so a page that redefines it can turn a `#fragment` move into a full load wait or the reverse. Live on Chrome Canary (2026-09), on a background scratch tab to a page on 127.0.0.1 and back: both loads took the page path (no `warning`) and the key process did not change, but Canary was already frontmost, so a raise could not show. Live on Canary behind Arc (2026-09): `navigate` of a shown scratch tab to `about:blank` took the page path and left the frontmost app, key process and cursor unchanged. Not yet measured on Arc and Safari.

## Permissions

1. **Browser:** Allow JavaScript from Apple Events. Chromium family: View > Developer (per profile). Safari: Develop menu.
2. **macOS Automation** for the controlling app (Claude Code, Terminal, iTerm) to each browser. Prompted on first call.

Each blocked layer returns an actionable error.

## Rules for changes

- **Single-file server, one runtime dependency.** Only `@modelcontextprotocol/sdk` plus Node built-ins at runtime, with no build step. `happy-dom` is a devDependency for tests only.
- **No user values in code.** JXA goes to `osascript` as one argument or one REPL line; runtime arguments are JSON. Page scripts read arguments only from `A`. User JS for `eval_js` is embedded through the wrappers.
- **The runtime stays self-contained ES2019.** It must not reference Node scope; `test/runtime.test.mjs` runs it under `node:vm` and compiles it with real osascript.
- **Tools earn their slot.** Solve a real workflow; don't mirror CDP. Check the known consumers (see GOALS.md) before changing the surface; GOALS.md has the admission test. Keep `tools/list` under `SCHEMA_BUDGET`, with shared guidance in `INSTRUCTIONS`. Turned down so far: a `find` tool (`accessibility_snapshot {query}` does it), a scroll tool (`eval_js` covers it), GIF recording (needs a dependency), and splitting `server.js` into modules.
- **Background-friendly by default.** Only `activate_tab` and calls passed `raise:true` (`screenshot`, `navigate`, trusted input) take focus, as `INSTRUCTIONS` says, and `new_tab` may focus the browser (its description says to defer it while the user works). Background trusted input must never change the user's AppKit key process or shared cursor.
- **Every improvement is measured.** Before committing a change to perch:
  1. Write the failing test first, then make it pass. `npm test` (unit, no browser) must be green.
  2. `npm run smoke` (live) must pass.
  3. `npm run bench` (live, Canary) compares against `bench/baseline.json`. It serves `bench/fixture.html` on 127.0.0.1, navigates an existing about:blank scratch tab there (shown, for the screenshot rows) and back, and records the fixture's sha256; byte counts are compared only when the baseline's hash matches. Say the before/after in the commit message. A regression needs a reason or a fix. Unchanged code moves about ±5% between runs, so smaller differences are noise.
  4. If the change made perch faster, replace `bench/baseline.json` with the new run (`bench/runs/bench.json`) in the same commit. For a change a user would notice in an agent's session (fewer calls, a flow that works now), rerun `scripts/compare.mjs` and add a row to `bench/compare/README.md`.

  Live steps need a browser the user isn't using; if none is free, say so and leave them for later rather than skipping silently. Runs land in `bench/runs/` (gitignored).
- **Live focus checks.** `npm run smoke` reuses an existing scratch tab and skips tab creation; `--with-tab-creation` opts into checks that may focus the browser. `scripts/trusted-live.mjs --background` needs an active scratch tab behind another app for SkyLight click; `--background-fill` tests an inactive scratch tab even while minimized; `--background-press` and `--background-select` (select {trusted} on `test/fixtures/trusted-select.html`) need the same active scratch tab as `--background`. `--new-tab` (plain clicks that open a tab, any browser) needs an about:blank scratch tab, shown in its window with `--background`, and closes the tabs it opened. `scripts/dialog-live.mjs` needs an existing about:blank tab active in its window. `scripts/navigate-live.mjs --arc` needs an about:blank tab in Arc's front window that the window doesn't show, with Arc in front (or another app in front for `--background`). If the preconditions are absent, defer; never create/select tabs or activate another app to create them. Preserve the user's foreground while testing.

## Ceiling: what AppleScript can't do

- **Network interception** (request/response capture, header injection): CDP or an extension only.
- **Pre-load instrumentation** (`document_start`): both bridges run after navigation.
- **Off-screen capture** of minimized windows or windows on another Space: neither capture path has a window image or CGWindowID for them.
- **Background trusted input:** live-verified on Chrome Canary on this macOS version. SkyLight is a private macOS API and can change between OS releases. The explicit `raise:true` HID route remains available.
