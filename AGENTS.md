# perch

Architecture and invariants for the perch MCP server.

perch exposes MCP tools for driving the user's own macOS browsers: tabs, navigation, JS evaluation, waits, screenshots, page text, accessibility snapshots, console capture, form input, file upload, notifications. It runs `osascript -l JavaScript` against each browser's AppleScript dictionary. No extension, no debug port. The tool surface is `TOOLS` in `server.js`; `SKILL.md` mirrors it for skill authors, and `test/docs.test.mjs` keeps the two in sync.

## Architecture

```
MCP client <--stdio--> server.js <--osascript REPL--> jxaRuntime --Apple Events--> Chrome / Arc / Safari / ...
                                                          \--tab.execute / doJavaScript--> page scripts
```

`server.js` has four layers, top to bottom:

1. **Transport.** `OsaDaemon` keeps one `osascript -l JavaScript` process per lane, running `DAEMON_LOOP`, which reads stdin lines itself (`osascript -i` over a pipe evaluates nothing until EOF on macOS 27.2). `jxa(script, {lane})` runs a script there, falling back to one-shot `execFile` only when the script never reached stdin.
2. **JXA runtime.** `jxaRuntime()` is a real function whose source is sent once per daemon as the prelude. It defines `globalThis.__perch` with the per-call entry points. Node calls `rt(fn, args)`, which sends one short line: `__perch.fn(<json>)`.
3. **Page scripts.** `PAGE_PRELUDE` plus `PAGE_SCRIPTS[name]` are plain strings that run inside the tab. `pageScript(name, A)` prepends `const A = <json>`, and `buildEvalWrapper` wraps the result.
4. **Tools.** Thin Node handlers (`HANDLERS`) validate arguments, call `rt` or `evalJs`, and shape results. `formatResult` maps them to MCP content.

**osascript daemon.** A warm REPL runs a realistic script in about 25ms against about 90ms cold. That saving is JXA bridge startup, not the fork.
- **Lanes:** there are two, `fast` and `slow`, so a polling `wait`, `select`, `navigate` or `awaitPromise` never blocks quick calls.
- **Framing:** each script is URI-encoded onto one line and evaluated inside an IIFE that prints a `<<P:<id>:O|E:...>>` marker. `encodeURIComponent` always escapes `<`, `>` and `:`, so markers can't collide with the payload. Output is scanned incrementally.
- **Start-up:** the prelude round-trip is the ready handshake; there is no fixed settle delay. The server calls `warm()` on both lanes once it is connected, so no tool call pays the cold start (live, a first call 800ms after start: 183 to 109ms on the fast lane, 199 to 60ms on the slow one). It never throws: a failed spawn leaves no process and the next call retries.
- **Failure policy:** a timeout or a mid-call exit rejects and kills the REPL, and the next call respawns it. So does `abort(err, token)`, which the dialog watchdog uses; it acts only while that job is still running. None is retried, because the script may already have opened a tab or posted a click. Only a script that never reached stdin (`notSent`) falls back to one-shot.
- **Off switch:** disable the daemon with `PERCH_DAEMON=0`.

**Targeting (`resolve`).** `procs()` does one `CGWindowListCopyWindowInfo` read, about 4ms. It gives the on-screen z-order of browsers, the frontmost app, and pids and CGWindowIDs. It replaces a System Events `frontmost` query, which took about 60ms per call and needed Automation permission for System Events.
- **Search order:** candidates are on-screen browsers topmost first, then the rest of `BROWSERS` in declared order, checked with `running()`.
- **Stopping:** the walk stops at the first match.
- **Window ids:** `win.id()` is read only when `windowId` was given.
- **Default target:** with no target, the active tab of the first window, read first as `windows[0].activeTab.id()` of the first candidate (one event on Chromium and Arc). A window showing no tab (a fresh Arc window) is skipped.
- **Tab handles:** clients never branch on browser. `tabId` is an opaque handle `<key>:<raw>` (`key` from `BROWSERS`, e.g. `arc:<uuid>`, `canary:<id>`), so `{tabId}` alone targets a tab in any browser. The key matters: Chromium tab ids are per-process counters and collide across Chromium apps. Safari tabs have no id, so theirs is `safari:<windowId>.<index>.<url hash>`: `resolveSafari` re-finds it by URL (nearest index wins), and a navigation makes it stale, which is why `navigate` returns the tab's current handle. A bare id from before handles is still searched across browsers.
- **Tab ids:** a handle resolves with one bulk `win.tabs.id()` read per window, then `tabs.byId`. Chrome and Arc targets are pinned by id even when given by position, because `tabs[i]` is re-evaluated on every use and a long poll could drift to another tab. Chrome has no tab `select` verb, so selection re-reads the position from the id.
- **Apple Event budget:** live, each Apple Event to a browser costs about one display frame (~16.7ms), while `procs()` and `running()` cost under 3ms, so latency is the event count; `test/perf-budget.test.mjs` pins it. `evalJs` first tries `quickExec`, one event: a Chromium handle through its remembered window (`hints`, filled by list_tabs, new_tab and resolve; `windows[w].tabs.byId(id)` can only miss, never hit another tab), a Safari handle through `windows.byId(win).tabs[i]` with the page checking its own URL hash first, or the default target's active tab. It falls back to `resolve` only when the script cannot have run (errAENoSuchObject, or the hash sentinel). Arc handles keep separate `arcHints` (a window that showed the tab, from list_tabs and resolve; never new_tab, whose tab is put behind), checked with one `windows[w].activeTab.id()` read; a hit or the default target marks the tab `shown`, so `isActive` costs nothing more: an Arc page call is 3 events (shown tab, url, execute). `wait`, `awaitPromise`, `select` and click readback only run page JS, so a hinted Chromium handle builds its tab with no event (`pageTarget`) and re-resolves once, on errAENoSuchObject only. `wait` tries `quickExec` first, then polls every 50ms. `list_tabs` reads all of an app's windows at once (`windows.tabs.url()` and friends: four events for Chromium and Safari, six for Arc), and a `urlContains` or `titleContains` no tab of a browser matches stops that browser after one read. Each browser's lister is a generator that yields after every event, and `listTabs` runs them in turns, one event each: frame phases differ per browser, so three browsers take about as long as the slowest alone (fake frame clock: 208 to 102ms; live with Canary, Arc and Safari open, `limit:10000` went from 205 to 101ms, and one browser alone is unchanged at 67ms), and a failed bulk read walks windows in the same turns and the same slot. Each browser reads first what its filters look at (urls when there is none; Arc its tab ids), and a browser whose earlier browsers are sure to fill `limit` (their exact rows once listed; before that, their first read: exact for Chromium and Safari with one filter, distinct ids or the best single window for Arc, nothing with two filters) is only counted for `total`, from the reads it already has. `test/list-tabs.test.mjs` checks rows and total against per-browser listings in random worlds. Window geometry is one `bounds()` read (Chromium fails `position()`, Safari only has `bounds`, and a failed read costs a full event); on Arc it is one `windows.name()` read. Never touch a quit app's windows (`alive`): JXA relaunches it.
- **Browser names:** `matchApp` (Node, in `handleCall`) matches `app` loosely: case-insensitive name, key, or a unique substring.
- **Errors:** thrown errors start with a browser-neutral code (`tab_not_visible`, `stale_tab`, `window_offscreen`, `no_browser`, `timeout`, `dialog_open`) that clients branch on. Tool descriptions and `INSTRUCTIONS` never name a browser; `test/runtime.test.mjs` enforces it. Permission messages are the exception, since the user needs the exact per-browser toggle. `tab_not_visible` never activates the tab for the caller; that is `activate_tab`'s opt-in.

**JXA access patterns.** Read collections lazily (`app.windows[i]`, `win.tabs[i]`), never with the called form (`app.windows()`). The called form loses the bridge context on Arc, and later property chains throw "Can't convert types". Multi-tab reads use bulk property access (`win.tabs.url()`), about 30x faster than per-tab loops. That's the difference between working and timing out on Arc windows with hundreds of tabs.

**Arc quirks.**
- **Double encoding:** Arc's `execute` JSON-stringifies whatever the page function returns, so `exec` unwraps one layer.
- **Reading the active tab:** `win.activeTabIndex()` and `win.currentTab` both throw. `win.activeTab.id()` works; it throws on a window showing no tab.
- **Tab order:** `win.tabs` order is unrelated to the sidebar (effectively random) and includes Favorites (`location` `topApp`). `win.activeSpace.tabs` is in sidebar order. `arcOrder` builds the display order (Favorites, then the active space's sidebar), and Arc's `tabIndex` means a row in it.
- **Shared windows:** windows on the same space share the same tab set (same UUIDs), and one tab can be active in several windows. `execute` works only through a window where the tab is active and hangs through any other, so `resolveById` prefers such a window. `select` changes only the window it's called through. `list_tabs` lists each Arc tab once, under the frontmost window showing it.
- **Switching tabs:** writing `activeTab`/`currentTab` is forbidden, but `tab.select()` switches without raising.
- **Background tabs:** `execute` hangs until timeout on a background tab and on its own `arc:` pages, so `visibleGuard` refuses first; `trustedTarget` refuses an `arc:` page for every trusted input, and `navigate` from or to one sets the url and runs no page JS until the tab reads a non-`arc:` url (set again after 1s, as `new_tab` does).
- **Geometry:** Arc has no window geometry verbs, so its frame comes from its own CGWindowList entry, matched by window title (`byTitle`). AppleScript windows and CG entries both run front to back, so same-titled windows pair up in order, but only when every window with that title has an entry; without CG titles (no Screen Recording grant) windows pair by position only when every window has one. Otherwise it is `window_offscreen`, since a minimized window has no entry and the pairing would name another window. Elsewhere `ids()` takes the CG entry nearest the window's frame, and only within 4pt in x and w and 120pt in y and h (the titlebar and toolbar CG counts), else `window_offscreen`; when another of the app's entries scores within 2pt of it, `ids()` marks the match `ambiguous` and trusted input and the frame walk refuse with `window_ambiguous` (screenshots don't check). `axPageArea` likewise takes the one AX window within 8pt of that frame, or, when `_AXUIElementGetWindow` reads their CGWindowIDs, the one whose id is the target's; zero or several is null (no page area).

**Eval runs in an isolated world (Chrome family).** Chrome runs Apple Events JS in an isolated world. The DOM and `location` are shared with the page; JS globals are not.
- **Persistence:** globals set by one eval persist for later evals; `window.__perch_refs` and `window.__perch_console` rely on this.
- **Page globals:** the page's own globals are invisible, so probe page state through the DOM.
- **Events:** a plain `click` still fires main-world handlers, because DOM events cross worlds.
- **Console:** `console_capture` injects a `<script>` that patches the main world's console and relays entries as `perch:console` events. A ping/pong tells whether it ran; under a CSP that blocks inline scripts it patches the isolated console instead, which sees only perch's own evals.
- **Network:** `console_capture {mode:"network"}` reads Resource Timing (`performance.getEntriesByType("resource")`), which the browser buffers without help, so it needs no start and intercepts nothing. A cursor on `window.__perch_net` drains new entries; the first read raises the buffer from 250 to 1000. Safari has no `responseStatus`, so status reads `-`. Patching `fetch`/XHR was rejected: it is close to interception.
- **Timers:** page timers are throttled to about 1/s in background tabs. Anything that must wait polls from JXA (`poll` in the runtime) instead of `setTimeout` in the page. `select` is start/pick/readback steps polled that way, and so is `click {readback}`: the click stores the readback element's text, a state signature and the url on `window.__perch_rb`, then JXA polls `readback_read` for up to 2s until any of them changes (a missing `__perch_rb` means a new document), or until the page has been quiet for 10 polls in a row (about 670ms live): no DOM mutation anywhere, seen by a MutationObserver armed with the state and disconnected on every exit, and no fetch/XHR resource timing entry completing. An update landing later than that with nothing happening in between reads as `changed:false`. The signature covers the element and its first 50 descendants: `aria-pressed`/`-checked`/`-selected`/`-expanded`, `disabled`, the checked state and value of inputs and the selected state of options, so a toggle that changes no text still reads `changed:true`; `class` stays out, since hover, focus and animation flip it during the poll; `readback` stays the text. Trusted clicks arm it with `readback_arm` just before posting and poll after restoring the cursor. `file_upload` that reads `shown:false` after the site cleared or replaced its input polls `file_upload_shown` through the runtime `wait` for up to 1s, since many sites render the file name a tick later; the result keys stay the same. A single `fill` with `checked` or `option` (and no `text`) runs as a one-field `fields` call and returns that field's own result.
- **Typeaheads:** plain `fill` on an input that is a typeahead (`role=combobox`, `aria-autocomplete` list/both, or a widget box holding a hidden companion input and a dropdown/menu/listbox; never a search box, `tel`, or an input whose box holds another control) types with keydown/input/keyup and no blur, stashes `window.__perch_ta` and returns `{pending}`. Node then runs the runtime `select` without a start step: `fill_ta_pick` polls for the widget's own options (its linked lists by select's `linkedLists` rule, where a repeated id resolves to the copy sharing the deepest ancestor with the control, since separate React roots can repeat react-select ids; else the box's dropdown; never the rest of the page, so an empty own list means keep waiting) and presses the best match by `taMatch`, comparing with accents folded (NFD, combining marks stripped; results keep the real text): exact, then each typed comma part equal to one of the option's parts in order (`Cordoba, Argentina` finds `Córdoba, Córdoba, Argentina`), then a prefix of the whole option, then a prefix of one of its words, then every typed word whole and in order. Several hits in the winning tier short of exact are a tie: nothing is pressed and the miss carries `ambiguous:true`, an error saying several matched (give a more specific text) and the `candidates`. An own list unchanged for 8 polls (about 400ms) ends the wait (`fill_ta_pick` answers `{settled}`): a tie at once, a list without a hit only once it changed from the first list seen after typing, which may be a debounce's stale one (a widget that renders its answer before the first poll still waits the full time). An empty or still-changing list keeps being polled. Without `[role=option]`, options are leaves matching `li` or an option/item/result class; a lone such leaf with two or more distinct visible children and no control inside is a results wrapper, and its children are the options. It polls 1s, then up to 3s only when a probe finds a hidden companion or an open or non-empty own list. `fill_ta_read` waits for the pick to show (input value, or a react-select control's text) and the companion to hold a value, then blurs once and checks again, since these widgets clear unpicked text on blur. A background tab's `blur()` fires no events, so when the page lacks focus `taBlur` also dispatches `blur` and `focusout` (React's onBlur listens to the latter). No match on a widget that expects a pick (a hidden companion, its own suggestions shown at any point, or text cleared on blur) restores the prior text and companion value and returns `{ok:false}` with any `candidates`; any other combobox keeps the text as `{ok:true, kind:"plain", note}`. React 18 applies an onBlur clear in a microtask after the blurring script ends, so `fill_ta_miss` blurs in one call and reads the settled value in later polls (300ms, then keeps). `fill {fields}` defers such a field like a custom combobox. Plain fields also pass on a digits match (one digit string ends the other, 7+ digits), for phone masks that reformat or drop a country code. Unverified on real sites: suggestion lists portaled away from the input with no `aria-controls`.

**Page scripts.** One prelude defines `vis`, `labelText`/`hintText`/`accName` (accessible-name precedence), `role`, `ident` (`role "name"`), `setNativeValue` (the prototype setter, which reaches React-controlled fields), `fire` and `resolveEl`.
- **Arguments:** every tool body reads its arguments from `A`; no user value is spliced into code.
- **Refs:** `resolveEl` treats a missing or detached ref as `{__perch_ref_miss}`, which `formatResult` turns into an error with a re-snapshot hint.
- **Snapshot:** `accessibility_snapshot` stores elements on `window.__perch_refs` (a plain object, since a Map breaks the JSON round trip). It emits a line format: a `# {header}` line, then `ref role "name" key=json... flags`. `query` tests each line without its ref; refs number only the kept lines, and the header adds `matched` (all matches, even past `max`). Visibility is `vis()` plus a snapshot-local `snapVis`: a radio or checkbox shrunk or faded to nothing is listed when one of its labels is visible, and a `role=combobox` input when its styled select box (`x__control`/`x-control`) is; neither when it or an ancestor is `display:none`. A combobox input's `value` is its own, else the box's single value or chip labels, and `form.requiredEmpty` counts it filled when the box shows one; required file inputs count too, and an input that is both `aria-hidden` and `tabindex=-1` (react-select's required stand-in) does not. `checked` also reads `aria-checked`, and `pressed`/`selected` read `aria-pressed`/`aria-selected`.
- **Names:** `labelWords` skips hidden descendants and popups inside a label (`[role=listbox]`, `[class*=dropdown]`, live regions). A field with no label (`labelText`) is named, before its placeholder, by `nearText`: the nearest earlier sibling of it or its 3 nearest ancestors, never past a list item, fieldset or form, and never text beside another control. These flow into `ident()` for every tool.
- **Select:** `select` reads options only from the target control's own list: its `aria-controls`/`aria-owns` targets (react-select's listbox id derives from its input id; Downshift and Radix popovers link that way), else a list in a wrapper holding no other control, else options that appeared after select opened it. `[cmdk-item]` counts as an option. Other open menus get Escape first (not a combobox inside the control's own popup, such as cmdk's search box), an open menu is never pressed (a press closes react-select), a closed one is pressed before it is focused, and a focus that fired no focus event (a background tab's `focus()` fires none, live on Canary) gets a synthetic one, since react-select opens from it; and the unfiltered list is matched before anything is typed: exact, then whole word, then word prefix, then every typed word whole and in order, never mid-word, with accents folded. On a native `<select>` several options in the winning tier short of exact are a tie, as for typeaheads: nothing is set and it returns `{ok:false, ambiguous:true}` with the tied options as `candidates` (of exact ones equal once folded, the one matching as typed wins); a custom list's tie still goes to the shortest. A filter (the text up to its first punctuation) is typed only when that finds nothing; a miss clears it, closes a menu select opened, and returns up to 30 `candidates`, so `text:""` lists them. A custom list's miss ends once the own list holds (`select_pick` answers `{settled}`): 3 polls for `text:""`, else 8 (about 400ms), and after a typed filter only once the list has changed since typing, so a debounce's stale list is not the answer; an empty list waits the full 2.5s. A text input's value and hidden companion are put back after a miss when opening or closing it changed them.
- **Shadow DOM:** the prelude's `deepAll` walks open shadow roots in document order. The snapshot, fill's label search, and the selector fallback in `resolveEl` use it; aria-labelledby resolves in the element's own root, and the focus header descends into shadow roots. Closed roots and iframes stay out of reach of page JS; iframe controls come from Accessibility (see Frames).
- **Keys and hover:** `press` (`parseKey` turns the chord into KeyboardEvent fields in Node) and `click {hover}` dispatch untrusted events, so they reach background tabs but get no browser defaults: no text is inserted and CSS `:hover` never matches. `press` emulates the defaults pages rely on unless keydown or keypress was prevented: Enter clicks a button or link, or submits a field's form (its default button if any, else `requestSubmit`); Space clicks buttons, checkboxes and radios; Tab moves focus through visible tabbables in DOM order. `keyCode` and `which` go in the event init: Chrome and Safari accept them there, and a property defined on the event in the isolated world is invisible to page handlers (live: they read 0).

**Tab indices are positional.** `tabIndex` is the tab's current position; opening or closing tabs shifts it. It is still accepted in `target` but no longer listed, and so is `windowId`; the `target` schema lists only `tabId` and `app`, and rows carry only the handle.

**Tab creation.** `new_tab` defaults to the browser in use (`defaultBrowser`: topmost on screen, else the system default browser if it runs, else any running one) and requires a running browser with an existing window. It never calls `activate()` and never changes which tab a window shows: it reads the shown tab first (Chrome `activeTabIndex`, Arc `activeTab.id()`, Safari `currentTab.index()`) and puts it back if the browser switched to the new tab (live, Canary did). That costs at most 3 Apple Events. The browser may still raise its window during creation; undoing that would take an activation, so when `procs().front` was another app before and is the browser after, the result carries `warning: "creating the tab brought the browser to the front"`. Chrome can evaluate JS in that background tab; trusted input and screenshots need a tab already active in its window. Do not create tabs while preserving the user's foreground. `close_tab` is the cleanup: it takes only an explicit `tabId` (no default target, so it can never close the user's tab by omission), refuses a window's last tab (Arc: the space's last tab), and never selects or activates anything. `scripts/smoke.mjs --with-tab-creation` checks both live on a scratch `about:blank#perch-<ts>` tab and records frontmost app and key process around them. Live on Chrome Canary (2026-09): the shown tab stayed put and the new row was not active; with Canary behind another app, creating the tab brought Canary to the front and the warning appeared; with Canary already in front there was no warning. `close_tab` returned `{ok:true}`, left 0 matching tabs, never moved focus, and a second close of the same handle was `stale_tab`. The Arc and Safari restore paths are covered only by the fake world.

**Screenshots.**
- **Capture:** the runtime entry `shot` reads a window's own pixels regardless of z-order, in the daemon: `CGWindowListCreateImage` with `IncludingWindow` and `BoundsIgnoreFraming` (no shadow), a `CGBitmapContext` downscale only when wider than `maxWidth`, and `NSBitmapImageRep` PNG or JPEG at 0.8, returned base64. It checks the grant with `CGPreflightScreenCaptureAccess` (never prompts).
- **Fallback:** without the grant, or on an empty image, Node spawns `screencapture -l <CGWindowID> -t png|jpg` (which asks for the grant) and `sips` when the image is wider than `maxWidth`; dimensions come from the PNG/JPEG header (`imageDims`).
- **Missing CGWindowID:** minimized windows and windows on another Space cannot be captured; perch refuses instead of returning another app's pixels.
- **Tab targeting:** only the active tab of a window is rendered. A background screenshot refuses an inactive `tabId` or `tabIndex`; `raise:true` is required to select it.

**File upload.** `file_upload` reads the file in Node and ships it base64 in one page call, where a `DataTransfer` sets the input's `files` (about 80 KB across the bridge, nothing in the agent's context). It stats the file first and refuses one over 25MB, or over 700KB without the daemon: a one-shot osascript takes the script as an argument, and base64 of 700KB is near the ~1MB argument limit. The 25MB cap is a guess, not yet tuned live. Rejected: the OS file dialog (takes the foreground) and a localhost server the page fetches from (Chrome's local-network prompt). Unverified on real sites: uploads a site sends asynchronously after `change`, which the result can't see.

**Trusted input.** `click {trusted:true}` and `fill {trusted:true}` default to background routes that do not explicitly activate the browser or move the cursor. Background fill directly uses Chrome's editing command in the targeted tab; the live scratch-page test verified a trusted input event and exact Unicode value in an inactive tab while its window was minimized, with no Canary key focus during continuous monitoring. Background SkyLight click needs an on-screen window and its active tab; its event did not reach a minimized window in the live probe. `raise:true` keeps the foreground HID route.

1. For clicks and raised input, `trustedTarget` resolves the browser, checks Accessibility with `AXIsProcessTrusted()` (which does not prompt), and gets the target pid, CGWindowID, and frame from `procs()` / `ids()`. With `raise:true`, `focus` pins the window by id before raising it, since `windows[i]` is positional. Default trusted fill uses page JS and needs no CGWindowID or Accessibility grant.
2. `skyInit` binds SkyLight event functions in JXA. The background route never posts `SLPSPostEventRecordTo` AppKit focus records: they made input reach Chrome but redirected the user's keyboard until the restore.
3. Background trusted clicks require the target tab to already be active in an on-screen browser window; they never switch tabs. With `raise:true`, `aim` selects the target tab. A hidden tab's `screenX` and `outerWidth` are stale, so `trusted_probe` retries until visible, scrolls the element into view, estimates the screen point, and arms event recorders. The estimate puts all horizontal chrome left of the page and ignores zoom, so `aim` corrects it: background clicks read the page's web area from the Accessibility tree (`axPageArea`: the `AXWebArea` whose shape matches the viewport, since a side panel is a web area too; its width over `innerWidth` is the zoom), because directed SkyLight moves never reached a background page live. The foreground HID path calibrates from a posted mouse move and falls back to the Accessibility tree. Results carry `aim` (`ax` or `mouse`) and a `calibration` trace. The estimate alone never clicks: the hit test below needs the page area, so without one the click is refused.
4. Background mouse events use `SLEventPostToPid` with target pid/window routing fields and `CGEventSetWindowLocation` set to the **window-local** point. The sequence includes a move primer and an off-screen click pair before the target pair. A Command flag on the down event lets WindowServer deliver to the background window; the up event has no Command flag, and Chrome receives an ordinary trusted click with `metaKey: false`. Passing a screen point to `CGEventSetWindowLocation` shifted the live Chrome click by the window's y-origin; the local point landed at the exact element center. Background fill instead uses `document.execCommand('insertText')` directly on the requested tab's field, including inactive or minimized Chrome tabs. It verifies the trusted event and exact value. The `raise:true` path uses `CGEventPost(kCGHIDEventTap)` for the click and the session tap for typing, then restores the cursor. `trusted_check` reports `hit` for routed clicks.

A trusted click posts only where the page itself is, since frames take only an `fN` ref (see Frames). The page checks come first and are cheap: `trusted_probe` refuses an element that is, or lies inside, an IFRAME, FRAME, OBJECT or EMBED before scrolling it, and one whose aim point `elementFromPoint` finds on or inside such an element (a wrapper or overlay with a frame over its center), before arming anything. A click by point has no element, so its one page call, `trusted_frames`, returns the frames' viewport rects (open shadow roots included); `pointOnFrame` places the point through `axPageArea`, else the page's origin estimate, and refuses a point inside any rect. A page that can't answer fails closed. Page JS can't see a frame inside a closed shadow root, and `elementFromPoint` returns the shadow host for any hit inside a shadow tree, so the last word is Accessibility's: `offPage` hit-tests the final screen point (`AXUIElementCopyElementAtPosition` on the browser's application element, bound in `axInit`) and walks `AXParent` from the hit (64 steps) to the first `AXWebArea`, which must be the page's own (`axPageArea`'s element, compared with `CFEqual`, else by frame within 1pt when `CFEqual` can't bind). Another web area first is an embedded frame, however it got there; none at all is browser UI, a bubble or a child window (a JS dialog). Those, a failed or unbound hit test, and no page area all refuse with nothing posted: "the point is not on the page itself (embedded frame or browser UI); ...". It runs for every trusted page click (selector, ref, x/y, background or raised) and for raised trusted fill's click, after `aim` fixes the point and before `arm` and any post. It costs AX reads only (about 4, plus the page area aim usually already read), no Apple Events (`test/perf-budget.test.mjs`). The hit test is application-scoped, so another app's window over the point does not count (the background route delivers to the pid and window anyway), but another window of the same browser over it does, and refuses. Everything runs after `trustedTarget`, so `raise:true` has already raised the window when it refuses: the point is only known once the tab is shown and, in the foreground, calibrated, and a hit test only means something on an on-screen window. Raised fill's probe clears the field before these checks, so a refused raised fill can leave it empty.

The earlier bare `CGEventPostToPid` / `SLEventPostToPid` delivery probes did not reach Chrome's page. The routed SkyLight sequence is a separate path. `skyClick` and `mouse` both reject a target point outside the window frame.

**Trusted press.** `press {trusted:true}` is for widgets that ignore synthetic keys (they check `isTrusted`, or rely on native defaults such as Tab focus, Enter in a combobox picker, Escape closing a native popup). `skyKey` posts a keyDown/keyUp pair with `SLEventPostToPid` to the browser pid only: no window fields, no Command flag (shift, 0x20000, is the only flag), and the key's Unicode string on both events (`\r`, `\u001b`, `\t`, `\u007f`, NS function-key characters for arrows, Home/End, PageUp/PageDown, forward Delete, F-keys). Only named keys are accepted; cmd/ctrl/alt chords are refused because real ones can fire browser menu shortcuts, and single characters stay with `fill`. The browser performs the key's real default, so nothing is emulated. `trusted_key_arm` focuses the element and records the first keydown and keyup on window; `trusted_key_check` is polled for up to 1s and gives `hit` (true: a trusted keydown with that key; false: untrusted or another key; null: none arrived). The key goes to the browser's key window and its focused element (live, with focus in the address bar Enter reloaded the tab), so before arming anything `keyFocusMiss` checks with Accessibility alone (no Apple Events): the pid's `AXFocusedWindow` must match, within 4px, exactly one of the pid's CG windows (`procs().byPid`) and that one must be the target's CGWindowID, and an `AXParent` walk (64 steps) from `AXFocusedUIElement` must reach the page's web area (`axPageArea`, matched by frame). Another key window, an ambiguous match, focus in the toolbar, a popup, a side panel or a bubble's window is `tab_not_visible` with a hint: a background trusted click on the page moves focus back into it, and another key window needs `click {trusted, raise}`. The walk stops at the first web area: when that is an embedded frame's (a captcha, a sign-in widget) the press is refused, since frames take only `click {trusted:true}`; `trusted_key_arm` likewise refuses an IFRAME, FRAME, OBJECT or EMBED as the element or as `document.activeElement`. Should the key still miss, `hit:null` carries an error. Also `trusted_key_arm` refuses a Tab from the page's last focusable element (shift+Tab: the first), which would move focus into the toolbar. Like the click it needs the tab its window shows; in the lab, keys reached a covered window but not a minimized one. Live-proven in the lab on Chrome Canary; Safari and Arc are unverified.
The background `mousedown` carries `metaKey: true` because of the WindowServer routing flag, while the resulting Chrome `click` carries `metaKey: false`. Pages that inspect modifiers on `mousedown` may behave differently; verify the resulting page state after critical actions.

Foreground typing creates keyboard events with virtual key 0 and text attached via `CGEventKeyboardSetUnicodeString`, then posts at the session tap. Chunks are split in Node (`chunkUtf16`: at most 20 UTF-16 units, never splitting a surrogate pair). Two traps, both of which make Chrome type "a" (key 0) instead of the text:
- the encoding is `NSUTF16LittleEndianStringEncoding` = `0x94000100`, not `0x14000100` (which yields nil data);
- the stock JXA signature of `CGEventKeyboardSetUnicodeString` rejects NSData bytes as `UniChar*`, so it is rebound with `void *` parameters.

Mouse event fields use raw indices, because `$.kCG*` constants aren't reliably bridged: 1 = click state, 11 = pressure (double).

`scripts/skylight-probe.js` proves SkyLight functions bind from pure JXA. `ObjC.bindFunction` registers the function on `$` (call `$.SLEventPostToPid(...)`) rather than returning it.

**Frames.** Page JS can't see into cross-origin iframes, so `accessibility_snapshot {frames:true}` reads them from the Accessibility tree. The runtime entry `snapshotFrames` runs the snapshot page script (which then also returns `innerWidth`/`innerHeight`, dropped from the header in Node) and walks in the same call. `axPageArea` picks the page's web area (it also returns the element), and a BFS bounded by node count (3000) and time (150ms) emits controls only inside nested `AXWebArea` nodes, so page-level controls stay with the page rows. Each row reads `AXRole`, `AXTitle`/`AXDescription`, `AXEnabled`, `AXExpanded`, the frame's `AXURL`, and `AXValue` only for a checkbox or radio's state. It never reads a field's value, and a secure field gets a `secure` flag so it can be handed to the user. A row whose center lies outside the window, the page area or its frame gets `offscreen`. Node formats rows as `fN role "name" frame="<host>" flags` (`role`, `query` and `max` apply) and keeps them in `frameRefs`, keyed by the handle the runtime resolved and replaced on that tab's next snapshot. They live in Node because the page can't see them and the REPLs respawn. `click {ref:"fN", trusted:true}` sends the ref's rows to `frameClick`, which keeps the row stored under the tab it resolves, walks again and matches by (frame URL, role, name, ordinal among equal role and name in that frame). It then clicks the fresh center through `skyClick` (`raise:true`: `leftClick`, cursor restored), never a stored point. A missing row, a changed frame URL or a changed page URL is the stale-ref error; an `offscreen` row is `{ok:false}`. Sign-in and challenge frames (`handoffFrame`: a short fixed host list, plus `/recaptcha` paths on google.com, so it needs the full frame URL) get a `handoff` flag, and so, failing closed, does a frame without an http(s) URL (about:blank, srcdoc, no `AXURL`) or one nested under a `handoff` frame (rows carry `up`, the ancestor frame URLs, which the click matches too); and a `handoff` or `secure` row is refused with `{ok:false}` before anything is raised, probed or walked; the runtime checks the stored row again (a ref that names an ordinary row in another tab) and the fresh row for `secure`. The result is `{ok, ref, frame, point, aim:"ax", delivery, before, after, hit:null}`: `before`/`after` re-read role, name, checked and `AXFocused` (plus `navigated` or `gone`), since no page recorder can confirm delivery; `after` is re-read every 50ms for up to 0.5s until something besides focus changes, because Accessibility trails the page. `checked` is null when `AXValue` isn't a boolean or number. Every other use of an `fN` ref (untrusted click, fill, press, select, get_text, file_upload) throws `frame refs need click {trusted:true}`. The walk fails closed with the trusted click's codes, but inside the header: without Accessibility, off the tab its window shows (`tab_not_visible`) or without a CGWindowID (`window_offscreen`), the page rows still return with `frames:{error}`. A default snapshot does no Accessibility work (`test/perf-budget.test.mjs`). Live on Chrome Canary (2026-09), with Canary behind another app and a page on 127.0.0.1 embedding a frame from localhost: the frame is a nested `AXWebArea` whose `AXURL` bridges, the button, checkbox and `aria-label`led password field got their names, the password row was flagged `secure` with no value, and trusted clicks on the frame's button and checkbox reached the page (`isTrusted` true; `after` showed the button's new name) with frontmost app, key process and cursor unchanged. A frame URL change made the old ref stale. Chrome gave the checkbox an empty `AXValue` whether checked or not, so its `checked` reads null. A `frames:true` snapshot took p50 162ms against 7ms for the default one (116 against 4 with Canary in front); the walk's own 150ms bound holds it. Links, `raise:true` frame clicks, Safari and Arc are unverified, and so is the hit test against a real challenge widget inside a closed shadow root. Rejected: a configurable hand-off host list.

**Dialogs.** A page's `alert`/`confirm`/`prompt` blocks its JS, so a call that runs page JS (often our own `el.click()` on a confirm button) hangs inside `execute` until the timeout. `rt()` watches every entry except `DIALOG_BLIND` (tab listing, creation, closing, activation, geometry, capture and the dialog entries): after `DIALOG_PROBE_MS` (1500) in flight, and every `DIALOG_REPROBE_MS` (2000) after, a one-shot osascript (never queued behind the hung lane) runs the runtime's `dialogs({target})` with the call's own target (no target: the default target, resolved as the call resolves it). A hit calls `OsaDaemon.abort` with `dialog_open`; the next call respawns the REPL. With `PERCH_DAEMON=0` it looks once, when the call times out, and rewrites the error. Dialogs fail closed: perch aborts a call, or answers a dialog, only when it can tie a JS alert/confirm/prompt to the target tab (`ownDialogs`); anything else is ignored by the watchdog (the plain timeout stands) and refused by `press {dialog}`, because answering the user's own dialog in another tab is worse than a refusal.
- **Scan** (`scanDialogs`): Accessibility only, no Apple Events, so a probe with no dialog open costs none (`test/perf-budget.test.mjs`). Live on Chrome Canary a dialog is its own window (subrole `AXUnknown`) holding, two levels down, a group with subrole `AXApplicationDialog`. Browser windows (`AXStandardWindow`) are never searched, because a page's own `role=dialog` maps to that subrole too. Without the grant (`AXIsProcessTrusted`, which never prompts) it finds nothing.
- **Shape whitelist:** structural, never by localized title. An `AXHeading` origin line ("x.test says") plus 1 button and no field (alert), 2 buttons (confirm), or 2 buttons and exactly one plain `AXTextField` (prompt), with only `AXGroup` and `AXStaticText` around them. A secure field, more fields, 0 or 3+ buttons, no heading, any other role (image, link, checkbox, list, pop-up...) or a tree too big for the 300-node walk makes it kind `other`: HTTP sign-in sheets (a credentials hazard), FedCM and passkey prompts, and most permission bubbles. The message is the static texts, or a prompt's field title.
- **Attribution:** Chrome's tab-modal dialog is a child window, and a child window sits directly above its parent in the CGWindowList. So the dialog's CG entry, matched to its AX frame within 4px among the pid's windows of any size (`procs().byPid`), must be followed by the target window's CGWindowID (`ids(t)`), and the target must be the tab its window shows (`isActive`). Ambiguous or missing means not attributed, and so does a target window that another of the browser's windows could be (`ids` marks it `ambiguous`). Apple Events (resolve, the shown tab, geometry) are spent only after the scan finds a candidate. This relies on Chrome answering property reads while a JS dialog is open, which is plausible (it suspends `execute` rather than blocking) but unverified live; if they fail, the dialog stays unattributed.
- **Proof:** a shape and a heading can be mimicked: a permission bubble or the multiple-downloads prompt reads "a.test wants to" over two buttons, the confirm shape. So both `press {dialog}` and the watchdog also need the heading to name the tab's host (case-insensitive, `www.` optional, as a whole host), which rejects "Leave site?" prompts, other origins' dialogs and cross-origin frames' dialogs (the watchdog then leaves the plain timeout), and a hostless page (about:, data:, file:, blob:) is refused. Last, the page must be paused: a JS dialog blocks its tab's JS, the browser's own prompts do not. `pagePaused` runs a no-op through `execWithin` (the bounded NSAppleScript execute, error Ref never read) with a 1s bound; a reply means the page runs, so `press {dialog}` refuses and the watchdog stays quiet. Only a timeout is proof. A fast failure (JavaScript from Apple Events off) or no bounded execute (Safari, Arc) is unproven and fails closed, so dialogs there are neither answered nor reported. The proof costs about 1s, only once a candidate passed the other checks.
- **Answering:** `press {dialog}` needs `target.tabId` (checked in Node and in the runtime), like `close_tab`, so it can never land on whatever tab happens to be in front. Buttons go by position (Enter the last, Escape the first), pressed with `AXPress`; a prompt's text is set as the field's `AXValue` and read back first. It never activates or raises. It polls up to 1s until the pressed dialog's own element stops answering `AXRole`; a dialog the page opens at once, even an identical one, is a new element and comes back as `next` (its kind). A background tab's dialog waits until its tab is shown, so the watchdog cannot see it. The page's own dialogs bring the browser forward by themselves (as `navigate` setting a url did, see Navigation) and take the keyboard (seen live with the browser behind another app: keys the user typed elsewhere landed in a prompt's field); that is the page, not perch, but it is why the live check must run while nobody types. The live check (`scripts/dialog-live.mjs`) targets Chrome Canary on a page it serves on 127.0.0.1, with a second-window case when a second scratch window exists; the attribution rules have not run live yet. Safari's and Arc's dialog trees are unverified. Rejected: auto-dismissing dialogs (a false `ok`), a dialog tool or `click {dialog}` (schema budget), and matching a dialog by browser alone (it answered dialogs in the user's other tabs).

**Navigation.** Live on Chrome Canary (2026-09): `navigate` from a scratch `about:blank` tab to a page served on 127.0.0.1, with Canary behind another app, brought Canary to the front (frontmost app and key process changed, found by checking after each call). `navigate` only sets the tab's `url` and never activates, so Chrome raised itself; a navigation the page started (`location.href` via `eval_js`) did not. Diagnosed live on Canary (2026-09): the raise comes from Chrome's AppleScript `set URL` itself (`t.tab.url = a.url`), which Chrome treats as a browser-initiated typed navigation and brings its window forward for, from an http page as well as from `about:blank`, and on a tab its window doesn't show (it did not select the tab). The bounded NSAppleScript execute alone did not raise, and page-JS `location.href` did not raise in two runs. `new_tab`'s `nt.url = a.url` is the same call, which fits its "may focus the browser" note. So `navigate` now starts the load from page JS: when page JS runs (Chromium, Safari, Arc's shown tab) and the URL is http(s) or `about:blank`, the stamp call also runs `location.assign(url)`. It sets `url` only when page JS can't run (Arc background tab, browser pages, JS from Apple Events off, no reply), the URL is anything else (`data:`, `javascript:`, relative), or `assign` throws; on Chromium that path returns `warning`. If the reply to the stamp call is lost, a loading tab or a document without the stamp at a different URL counts as started, so the URL is never loaded twice; not when the tab was already loading before the stamp, since an earlier load looks the same. A page-started load is not a typed one: the old page is the referrer, `beforeunload` can run (and show its dialog if the user interacted with the page), and the page's own rules (sandbox, CSP) apply. The page can cancel it: a Navigation API `navigate` listener that calls `preventDefault` is seen by the stamp call, which then sets `url` with the `warning`; a load dropped any other way (the user stays on a `beforeunload` dialog) looks like a download or 204, so once `loading` settles with the tab's URL unchanged `navigate` returns `waited:false` rather than load it again. The stamp call's same-document check uses the page's global `URL`, so a page that redefines it can turn a `#fragment` move into a full load wait or the reverse. Live on Chrome Canary (2026-09), on a background scratch tab to a page on 127.0.0.1 and back: both loads took the page path (no `warning`) and the key process did not change, but Canary was already frontmost, so a raise could not show. Live on Canary behind Arc (2026-09): `navigate` of a shown scratch tab to `about:blank` took the page path and left the frontmost app, key process and cursor unchanged. Not yet measured on Arc and Safari.

## Permissions

1. **Browser:** Allow JavaScript from Apple Events. Chromium family: View > Developer (per profile). Safari: Develop menu.
2. **macOS Automation** for the controlling app (Claude Code, Terminal, iTerm) to each browser. Prompted on first call.
3. **macOS Accessibility**, for SkyLight/HID input (trusted clicks and raised input).

Each blocked layer returns an actionable error.

## Rules for changes

- **Single-file server, one runtime dependency.** Only `@modelcontextprotocol/sdk` plus Node built-ins at runtime, with no build step. `happy-dom` is a devDependency for tests only.
- **No user values in code.** JXA goes to `osascript` as one argument or one REPL line; runtime arguments are JSON. Page scripts read arguments only from `A`. User JS for `eval_js` is embedded through the wrappers.
- **The runtime stays self-contained ES2019.** It must not reference Node scope; `test/runtime.test.mjs` runs it under `node:vm` and compiles it with real osascript.
- **Tools earn their slot.** Solve a real workflow; don't mirror CDP. Check the known consumers (see GOALS.md) before changing the surface; GOALS.md has the admission test. Keep `tools/list` under `SCHEMA_BUDGET`, with shared guidance in `INSTRUCTIONS`. Turned down so far: a `find` tool (`accessibility_snapshot {query}` does it), a scroll tool (`eval_js` covers it), GIF recording (needs a dependency), and splitting `server.js` into modules.
- **Background-friendly by default.** Only `activate_tab`, `screenshot {raise}` and trusted input with `raise` take focus. Background trusted input must never change the user's AppKit key process or shared cursor.
- **Every improvement is measured.** Before committing a change to perch:
  1. Write the failing test first, then make it pass. `npm test` (unit, no browser) must be green.
  2. `npm run smoke` (live) must pass.
  3. `npm run bench` (live, Canary's shown tab) compares against `bench/baseline.json`. Say the before/after in the commit message. A regression needs a reason or a fix. Unchanged code moves about ±5% between runs, so smaller differences are noise.
  4. If the change made perch faster, replace `bench/baseline.json` with the new run (`bench/runs/bench.json`) in the same commit. For a change a user would notice in an agent's session (fewer calls, a flow that works now), rerun `scripts/compare.mjs` and add a row to `bench/compare/README.md`.

  Live steps need a browser the user isn't using; if none is free, say so and leave them for later rather than skipping silently. Runs land in `bench/runs/` (gitignored).
- **Live focus checks.** `npm run smoke` reuses an existing scratch tab and skips tab creation; `--with-tab-creation` opts into checks that may focus the browser. `scripts/trusted-live.mjs --background` needs an active scratch tab behind another app for SkyLight click; `--background-fill` tests an inactive scratch tab even while minimized; `--background-press` needs the same active scratch tab as `--background`. `scripts/dialog-live.mjs` needs an existing about:blank tab active in its window. If the preconditions are absent, defer; never create/select tabs or activate another app to create them. Preserve the user's foreground while testing.

## Ceiling: what AppleScript can't do

- **Network interception** (request/response capture, header injection): CDP or an extension only.
- **Pre-load instrumentation** (`document_start`): both bridges run after navigation.
- **Off-screen capture** of minimized windows or windows on another Space: the rect fallback needs the window on top.
- **Background trusted input:** live-verified on Chrome Canary on this macOS version. SkyLight is a private macOS API and can change between OS releases. The explicit `raise:true` HID route remains available.
